### A1. หน้ากรอกผลบริการ (IG/IC) ให้ใช้ง่าย
**ปัญหา:** ก่อนถึงงานจริงต้องผ่านช่องค้นหา (ซ้ำกับแถบบน), ตัวกรอง 4 ช่อง, การ์ดสถิติ 5 ใบ และคำอธิบายยาว 4 ก้อน

**แนวทาง:**
- เปิดหน้ามาเจอรายชื่อลูกค้าที่ **ยังไม่กรอก** ของทีมตัวเองทันที พร้อมแถบความคืบหน้า (เช่น เหลือ 20 จาก 24)
- ตัวกรองย่อเหลือบรรทัดเดียว "พุทธมณฑล · ทีม A · ต.ค. 2026 [เปลี่ยน]" ค่าเริ่มต้นมาจากบัญชีผู้ใช้
- ย้ายการ์ดสถิติสถานีไปหน้าสรุป
- ปุ่มใหญ่ "ปกติทั้งหมด · ปิดงาน" คงไว้เป็นทางหลัก
- 3 หมวด (พบปลวก / เปลี่ยนไม้ / งานซ่อม) พับไว้ กดเปิดเฉพาะเมื่อมี
- ปริมาณเหยื่อเป็นปุ่มกด 50 / 100 / 150 / 200 แทน dropdown
- ปุ่ม "บันทึก + ลูกค้าถัดไป"
- บันทึกร่างอัตโนมัติ กันข้อมูลหาย

**แบบที่เจ้าของเลือก (10 พ.ย. 2026) — ซ้ายแบบ A + ฟอร์มแบบ B:**
- **ฝั่งซ้าย:** ตัวกรอง เขต / สาขา / ทีม / เดือน · ช่องค้นหาช่องเดียว พิมพ์ชื่อลูกค้า **หรือ** เลขที่สัญญาก็ได้ · แถบความคืบหน้า · สลับ "ยังไม่กรอก / กรอกแล้ว" · รายชื่อลูกค้าพร้อมป้าย Tier และป้ายจำนวนกล่อง AG ที่ยังติดตามอยู่
- **ค้นหาคำใกล้เคียง:** ถ้าพิมพ์แล้วไม่พบตรงตัว ระบบเสนอรายที่สะกดใกล้เคียงให้กดเลือก (เช่น พิมพ์ "เมืองทอน" เสนอ "เมืองทองคลังสินค้า")
- **ทีม:** ทีมเปลี่ยนลูกค้าที่ดูแลบ่อย → ตัวกรองทีมเริ่มที่ "ทุกทีม" · ในฟอร์มมีช่อง "ทีมที่เข้า" เติมค่าจากครั้งก่อนให้ แก้ได้ทุกครั้ง (D8 ยืนยันแล้ว) · ทีมจึงเป็นข้อมูลของ "การเข้าบริการแต่ละครั้ง" ไม่ใช่ของลูกค้า
- **ฝั่งขวา:** ฟอร์มทีละราย — วันที่เข้า, ทีมที่เข้า, ปุ่มใหญ่ "IG / IC ปกติทั้งหมด", ปุ่มเลือกสิ่งที่พบ 4 ปุ่ม: พบปลวก / เปลี่ยนไม้ / งานซ่อม / กล่อง AG, ปุ่ม "บันทึก + รายถัดไป"
- **กล่องเหยื่อ AG อยู่ในฟอร์มเดียวกัน:** ติดกล่องใหม่ (S) และกรอกผลติดตาม (F) ของแต่ละจุดได้ในรอบบริการเลย · เลขรอบ F นับให้อัตโนมัติ · ลูกค้าที่มีกล่องค้างติดตาม ส่วน AG เปิดให้เองโดยไม่ต้องกด
- **กันลืมกล่อง (D10 ยืนยันแล้ว):** ปุ่ม "IG / IC ปกติทั้งหมด" ปิดเฉพาะส่วน IG/IC · ถ้าลูกค้ามีกล่อง AG ค้างติดตาม ต้องกรอกผลของกล่อง หรือติ๊ก "รอบนี้ไม่ได้ตรวจกล่อง" ก่อน ถึงจะบันทึกได้ · ถ้ายังไม่ทำ ให้แจ้งข้อความข้างปุ่มบันทึกว่าขาดอะไร
- **หน้ากล่องเหยื่อ AG เดิม:** ลดเหลือ "กล่องเหยื่อ AG นอกรอบ" ใช้กรอกงานกล่องที่ไม่ได้เข้าพร้อมรอบบริการ — ทั้งผลติดตาม (F) **และติดกล่องใหม่ (S)** (D9 ยืนยันแล้ว) ใช้ฟอร์มชุดเดียวกับข้างบน เพิ่มช่องเลือกประเภทรอบ (ติดตามผล / แก้ปัญหา) · การ์ดสถิติกล่องและสรุปการใช้เหยื่อย้ายไปหน้าสรุป

**ผลต่อฐานข้อมูล:** ไม่ต้องเปลี่ยนโครงตาราง — `visits.team_id` มีอยู่แล้ว · ผลกล่อง AG ที่กรอกในรอบบริการบันทึกเป็น `station_checks` ของ visit รอบนั้น และ `follow_up_no` ยังนับต่อสถานีเรียงตามวันที่เหมือนเดิม (SPEC §7.5)

**ไฟล์:** `docs/mockup/aga-bait-registry-prototype.html` (ส่วน `#s-service` และ `#s-bait`, `#s-summary`) · `SPEC.md` §8 หน้า 5 และ 6

### A3. แนบไฟล์ตอนเปิดงานให้ง่าย — ✅ **เจ้าของตัดสินแล้ว 10 พ.ย. 2026 (ทำใน mockup แล้ว)**
- ~~ลากไฟล์ PDF วางบนแถว~~ / ~~ลากหลายไฟล์จับคู่ตามชื่อ~~ → **ไม่ทำ** ใช้ปุ่ม "เลือกไฟล์" ที่แถวของสัญญานั้นเหมือนเดิม

- **รับไฟล์ได้ไม่เกิน 10 MB แล้วบีบให้เหลือไม่เกิน 5 MB** (เจ้าของสั่ง 10 พ.ย. บ่าย): ≤ 5 MB รับเลย · 5–10 MB ระบบบีบให้ · **เกิน 10 MB ปฏิเสธทันที** "ไฟล์ขนาดใหญ่เกินไป" · บีบแล้วยังเกิน 5 MB → ไม่รับ + บอกให้สแกนใหม่
- ⏳ **ยังรอเจ้าของตอบ:** ตัวกรอง "ยังไม่แนบไฟล์" พร้อมจำนวนที่ค้าง — เอาหรือไม่
- ⚠ **ต่างจากที่ตัดสินเมื่อเช้า 10 พ.ย.** ("10 MB · ไม่บีบอัตโนมัติฝั่งระบบในเฟส 1") — เพดาน 10 MB เหมือนเดิมแต่เป็นเพดาน "รับเข้า" และเพิ่มการบีบเหลือ 5 MB · เจ้าของสั่งใหม่ จึงถือตามนี้ · ผลต่อ build: ต้องมีตัวบีบ PDF จริง (ดู `docs/คู่มือสแกนและแนบไฟล์สัญญา.md` หัวข้อ "ที่ยังต้องตรวจ")

## ส่วนที่ 4 — ฐานข้อมูลและค่าใช้จ่าย

### C1. ค่าใช้จ่าย
ตัวข้อมูลมีขนาดเล็ก (กรอกเฉพาะจุดผิดปกติ) คาดว่าใช้หลายปีไม่ถึง 500 MB · ส่วนที่ใช้พื้นที่คือไฟล์ PDF: ประมาณ 1,200 สัญญาต่อปี × 2–5 MB (ค่าสมมติ ต้องวัดจากไฟล์จริง) = 2.4–6 GB ต่อปี

| ทาง | ต่อเดือน | ข้อแลก |
|---|---|---|
| ก. ฟรีทั้งหมด | $0 | ที่เก็บไฟล์ 1 GB, ไม่มี backup รายวัน, Vercel แพ็กเกจฟรีสงวนสำหรับงานไม่เชิงพาณิชย์ |
| ข. ทดสอบบนฟรี → go-live ด้วย Supabase Pro + Vercel Pro 1 ที่นั่ง **(แนะนำ)** | ประมาณ $45 | มี backup รายวัน, ที่เก็บไฟล์ 100 GB |
| ค. Supabase Pro + เก็บ PDF ใน Google Drive ของบริษัท (ระบบเก็บเฉพาะลิงก์) | ประมาณ $25 | ลิงก์หลุดได้, คุมสิทธิ์ผ่าน Drive ยากกว่า, ใช้งานหลายขั้นกว่า |

ราคาอ้างจาก SPEC §3 — **ต้องตรวจราคาปัจจุบันอีกครั้งก่อนตัดสิน**

**วิธีคุมค่าใช้จ่าย:**
- จำกัดขนาด PDF
- ประวัติการแก้ไขเก็บเฉพาะช่องที่เปลี่ยน ไม่เก็บทั้งแถว
- ไม่เปิด realtime (SPEC ยอมให้ข้อมูลช้าได้ 15–30 นาที)
- ผู้พัฒนา 1 ที่นั่ง
- ฐานข้อมูลตั้งที่สิงคโปร์ที่เดียว

### C2. โครงสร้างให้ดูแลง่ายระยะยาว
- แอปเดียว ไม่แยกหลายระบบ
- สูตรคำนวณทั้งหมดอยู่ใน `lib/rules` เป็น pure function มี unit test (กรณีบังคับตาม CLAUDE.md)
- ชิ้นส่วนหน้าจอกลางใช้ซ้ำทุกหน้า: โครงหน้า, ตาราง, ลิ้นชักประวัติ, ช่องแนบไฟล์ — **ไม่ยก CSS ที่ก็อปซ้ำใน mockup 9 ไฟล์ไปใช้จริง**
- ค่าที่เปลี่ยนได้เก็บเป็นตาราง (ตำแหน่ง, ประเภทลูกค้า, เกณฑ์ Tier) ไม่ฝังในโค้ด
- กฎสิทธิ์ RLS เขียนเป็นฟังก์ชันกลางชุดเดียว ทุกตารางเรียกใช้ ไม่ก็อปเงื่อนไข
- ชนิดข้อมูล TypeScript สร้างจาก schema ของ Supabase อัตโนมัติ
- ตรวจอัตโนมัติทุกครั้งที่ push: type check + lint + test
- ฐานข้อมูลทดสอบแยกจากของจริง

### C3. migration ที่ต้องเขียนตอน build (รวมจากทุกรอบ)
- `month_closures` key = (`month_key`, `scope`)
- `monthly_branch_snapshots` เพิ่ม `v_s1…v_xl3`, `report_cust`, `report_value`, `confirmed_at`, `confirmed_by`
- `profiles` เพิ่ม `username`, `is_active`, `must_change_password`, `last_login`, `position_code`
- ตาราง `positions` (ใหม่)
- ตารางไฟล์แนบสัญญา + เวอร์ชัน (ใหม่ — รอ D7)
- `audit_log` เพิ่มช่อง `branch_id`, `contract_id`, `month_key` + index สำหรับค้น
- `profiles` เพิ่มช่องจำสถานะบทสอนใช้งานครั้งแรก (เสนอ `onboarding_completed_at`, `onboarding_skipped_at`) — งาน E1 (D11–D13 ตอบแล้ว)

## ส่วนที่ 6 — ขั้นสุดท้ายก่อนส่งมอบให้ผู้ใช้จริง

### E1. สอนใช้งานครั้งแรกแบบเกม + คู่มือการใช้งาน (เจ้าของสั่ง 10 พ.ย. 2026)

**สิ่งที่เจ้าของต้องการ:**
- ทำเมื่อ production เสร็จครบแล้ว ก่อนส่งให้ผู้ใช้จริง
- มีคู่มือการใช้งาน และ/หรือบทสอนแบบเกมให้ผู้ใช้ลองทำจริงในโปรแกรม
- เหมือนเกมที่สอนวิธีเล่นตอนเข้าครั้งแรก — ถ้าเข้าใจแล้ว **กดข้ามได้เลย**
- **แยกหมวดตามสิทธิ์** ของบัญชีนั้น (สอนเฉพาะสิ่งที่ตำแหน่งนั้นใช้)
- เริ่มเองตอน **เข้าระบบครั้งแรก** ด้วย username + รหัสผ่านชั่วคราว (ที่ยังไม่ได้เปลี่ยน)

**แนวทาง (รูปแบบหลักยืนยันแล้วตาม D11–D13 ด้านล่าง · รายละเอียดหน้าตายังต้องทำ preview ให้เจ้าของดูก่อนตามกฎ UI):**
- **บทเรียนแยกตามตำแหน่ง** (อ่านจาก `profiles.position_code`):

| ตำแหน่ง | บทเรียน (ลำดับ) |
|---|---|
| Admin (เปิดงาน) | เปิดงานเข้าทะเบียน → แนบไฟล์สัญญา → ดู/ค้นทะเบียน |
| หัวหน้างาน | สถานะทะเบียนบริการ → กรอกผลบริการ (ปุ่ม "IG / IC ปกติทั้งหมด", พบปลวก, กล่อง AG) → AG นอกรอบ → ลูกค้ารอเก็บสถานี → ส่งข้อมูลและสรุปงานประจำเดือน |
| Project Manager / OM | ภาพรวมทุกเมนูแบบย่อ → จัดการผู้ใช้ → ตั้งค่า → ลงข้อมูล Port ต่างจังหวัด → Dashboard Sync → ประวัติการแก้ไข |
| ผู้ดูทั่วไป (viewer) | ไม่มีบัญชี จึงไม่มีบทเรียน — ถ้าต้องการ ใส่คำอธิบายสั้นบนหน้า Dashboard สรุปมูลค่า |

- **รูปแบบ:** ไฮไลต์ปุ่มที่ต้องกด + กล่องคำอธิบายสั้น 1–2 บรรทัด + ตัวนับ "ขั้น 3 / 8" + ปุ่ม **ข้ามขั้นนี้** และ **ข้ามทั้งหมด** · ให้ผู้ใช้ลงมือกดเอง ไม่ใช่อ่านอย่างเดียว · กด Esc = ข้าม · ใช้ได้ทั้งจอคอมและมือถือ
- **โหมดฝึก:** ใช้ข้อมูลตัวอย่าง ไม่บันทึกลงฐานข้อมูลจริง — กันข้อมูลฝึกปนทะเบียนจริง ปนตัวเลขที่ส่ง Dashboard และปนประวัติการแก้ไข
- **ดูซ้ำได้:** เมนู "สอนใช้งาน" ที่มุมขวาบน เลือกบทที่อยากดูซ้ำ · ลิงก์ไปคู่มือจากที่เดียวกัน
- **คู่มือ:** หน้าคู่มือสั้นแยกตามตำแหน่ง (เปิดในระบบ + พิมพ์/บันทึกเป็น PDF ได้) ใช้ภาพหน้าจอจริงหลัง production นิ่ง
- **จำว่าใครเรียนแล้ว:** เพิ่มช่องใหม่ใน `profiles` (เสนอ `onboarding_completed_at`, `onboarding_skipped_at`) **ไม่ผูกกับ `must_change_password`** — เพราะช่องนั้นกลับเป็น true ทุกครั้งที่ host รีเซ็ตรหัสผ่าน ถ้าผูกกัน ผู้ใช้เก่าจะเจอบทเรียนซ้ำทุกครั้งที่ลืมรหัส → ต้องเป็น migration ใหม่ (เพิ่มในรายการ C3)
- **เนื้อหาบทเรียนเก็บเป็นข้อมูล** แยกจากโค้ดหน้าจอ (1 ชุดต่อ `position_code`) — เพิ่มตำแหน่งใหม่หรือแก้ข้อความได้โดยไม่แก้หน้าจอ

**ลำดับที่ผู้ใช้ใหม่เจอ (ตาม D11–D13):** login ด้วยรหัสชั่วคราว → หน้าบังคับเปลี่ยนรหัสผ่าน → เข้าระบบครั้งแรก บทเรียนของตำแหน่งตัวเองเริ่มเอง (ข้อมูลตัวอย่าง) → จบหรือกดข้าม → ใช้งานจริง · ดูซ้ำได้จากเมนู "สอนใช้งาน"

**เสร็จ =** บัญชีใหม่ทุกตำแหน่งเข้าครั้งแรกแล้วเจอบทเรียนของตำแหน่งตัวเอง · ข้ามได้ทุกขั้น · ดูซ้ำจากเมนูได้ · รีเซ็ตรหัสผ่านแล้วบทเรียนไม่เด้งซ้ำ · ไม่มีข้อมูลฝึกเข้าฐานข้อมูลจริง · คู่มือครบทุกตำแหน่ง
