## ตรวจไฟล์ต้นฉบับ (`fixtures/dashboard_data.json`)
- 22 เดือน JAN.25–OCT.26 · ครบ 43 สาขาทุกเดือน · 16 ฟิลด์ทุกแถว · ไม่มีสาขาซ้ำ — ตรงกับที่หมวด 4 แจ้ง
- ชื่อสาขาทั้ง 43 ตรงกับ `lib/dashboard/branches.ts` **และ** ตาราง `branches` (seed ใน migration) ทุกตัวอักษร
- cust = ผลรวม 8 tier ทุกแถว · value = vS+vM+vL+vXL ทุกแถว · ไม่มีค่าติดลบ · จำนวนเป็นจำนวนเต็มทุกช่อง
- **ทศนิยม:** ไฟล์ใน fixtures **ไม่มี**ตัวเลขทศนิยมยาวแบบ `1600595.4100000001` เลย (0 ตัว) · มีรูป `.0` 1 ตัว · มูลค่าสูงสุด 17,350,612.80 (พอดีกับ numeric(14,2))
  → ไฟล์ที่หมวด 4 เห็นบน repo Dashboard อาจเป็นคนละรุ่นกับใน fixtures — ตัวแปลงรองรับทั้งสองแบบอยู่แล้ว

### วิธีเก็บเงินให้ตรง 100%
แปลงเป็น **สตางค์ (จำนวนเต็ม)** ก่อน: เศษ float ที่ต่ำกว่า 0.001 สตางค์ (เช่น `…0.4100000001`) ตัดทิ้งได้เพราะค่าจริงคือ .41 · ถ้ามีทศนิยมหลักที่ 3 **จริง** → หยุดทั้งไฟล์ ไม่ปัดเงียบๆ · เทียบยอดทุกจุดด้วยสตางค์ ไม่เทียบ float ตรงๆ

## ตรวจ RLS / constraint / trigger กับแถว legacy (อ่าน migration — ไม่ต้องแก้ schema)
| ด่าน | ผลกับแถว legacy |
|---|---|
| คีย์หลัก | `(month_key, branch_id)` — **ไม่รวม source** (brief เขียนว่ารวม) · แถว legacy อยู่ร่วมกับ computed/manual ของเดือนเดียวกันไม่ได้ → ใช้ได้เพราะ legacy อยู่ก่อน go-live (2026-10) เท่านั้น · ตัวนำเข้าเช็กก่อน: เจอแถวที่ไม่ใช่ legacy ในเดือนนั้นแม้แถวเดียว = หยุด ไม่เขียนทับ |
| `month_key` | ต้องเก็บ `YYYY-MM` (sync เทียบ string กับ go-live · ถ้าเก็บ `SEP.26` แถว legacy หายหมด) → ตัวแปลงเก็บ `YYYY-MM` |
| RLS เขียน | `snapshots_host_write` (host) หรือ service_role · ตัวนำเข้าใช้ service_role ผ่าน PostgREST **ไม่ใช้ role postgres** |
| RLS อ่าน | ผู้ล็อกอินอ่านตาราง · anon อ่านผ่าน `v_branch_summary` (ไม่มีข้อมูลลูกค้า) — ไม่กระทบ |
| CHECK report_cust/report_value | บังคับเฉพาะ `source='manual'` → legacy ผ่าน (ไม่ส่ง report_*) |
| audit trigger | ทำงานเฉพาะ `source='manual'` → **นำเข้า legacy ไม่ลง audit_log** (ดูข้อให้เจ้าของตัดสิน) |
| `v_s1…v_xl3`, `value_annual` | `NOT NULL DEFAULT 0` → ว่างไม่ได้ ได้ค่า 0 เอง (ไม่ได้เติมตัวเลขเดา) |
| go-live | ตัวนำเข้าอ่าน `go_live_month()` จาก DB (ค่าเริ่ม 2026-10-01) ไม่ hardcode · `oldest_open_month` ใช้ go-live ไม่ได้เดาจาก legacy |

## วิธีนำเข้า (ฐานข้อมูลในเครื่องเท่านั้น)
1. ขอคิว DB ในเครื่องจาก HQ ผ่านหมวด 4
2. ตั้ง env `NEXT_PUBLIC_SUPABASE_URL` (http://127.0.0.1:54321) + `SUPABASE_SERVICE_ROLE_KEY` (จาก `npx supabase status`)
3. ตรวจก่อน (ไม่เขียน):
   `npx vite-node --config vitest.config.ts scripts/import-legacy-snapshots.ts -- --file "<path>/fixtures/dashboard_data.json"`
4. เขียนจริง: เติม `--apply` — เขียน 903 แถว **ในคำขอเดียว** (สำเร็จทั้งหมดหรือไม่เขียนเลย) แล้วอ่านกลับเทียบทุกช่อง · รันซ้ำได้ (ทับแถว legacy เดิมด้วยค่าเดียวกัน)
- script หยุดทันทีถ้า URL ไม่ใช่ localhost (กันเขียน cloud)

## ต้องให้เจ้าของตัดสิน
1. **ภูเก็ต / สุราษฎร์ธานี** ไฟล์เดิมเขียนเขตสลับกันช่วง JAN–OCT.25 — เป็นการพิมพ์ผิดในไฟล์ หรือสาขาย้ายเขตจริง? (ตอนนี้ใช้เขตปัจจุบันตามกฎเดิม: ภูเก็ต เขต 11 · สุราษฎร์ธานี เขต 10)
   - ก) ใช้เขตปัจจุบันเหมือนพระราม 2 / ปราจีนบุรี (ไม่ต้องทำอะไรเพิ่ม · แนะนำ)
   - ข) ตรวจกับทีมก่อน ถ้าไฟล์ผิดก็ไม่ต่างจาก ก)
2. **ไม่มี audit_log ตอนนำเข้า legacy** (trigger จดเฉพาะแถว manual) — CLAUDE.md กฎ 7 พูดถึงการแก้ข้อมูล ส่วนนี้เป็นการนำเข้าครั้งเดียว
   - ก) ยอมรับ ให้รายงานนี้ + ผลรันเป็นหลักฐาน (แนะนำ)
   - ข) ให้หมวด 2 เพิ่ม trigger จด legacy ด้วย (ต้องเป็น migration ใหม่)
3. **ค่า 0 ใน `v_s1…v_xl3` และ `value_annual` ของแถว legacy = "ไม่มีข้อมูล"** ไม่ใช่ศูนย์จริง ผลกระทบ:
   - `v_branch_summary` จะโชว์ `value_annual = 0` ของเดือน legacy
   - กฎ 5.12a (ต่างจังหวัดเดือนแรกยกค่า legacy) — ถ้าหน้า 9 จะเติมฟอร์ม 8 tier จากแถว legacy จะได้แค่ยอดกลุ่ม (vS…vXL) ไม่มีมูลค่าราย tier → หน้าจอต้องรู้ว่าแถว legacy ไม่มีค่าราย tier
