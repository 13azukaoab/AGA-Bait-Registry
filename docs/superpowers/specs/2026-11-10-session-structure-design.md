# เอกสารออกแบบ — โครงสร้างการทำงานหลาย session (AGA Bait Registry)

> จัดทำ 10 พ.ย. 2026 · เจ้าของอนุมัติผังแล้ว (รอบ brainstorming)
> **เอกสารนี้ตอบว่า "ทำงานร่วมกันยังไง"** — ส่งงาน ตรวจ รวมเข้า `main` รายงาน และกติกากันข้อมูลปนกัน
> **ไม่ซ้ำกับ `docs/แบ่งงาน-5-หมวด.md`** ซึ่งตอบว่า "หมวดไหนทำอะไร แตะไฟล์ไหน เปิดได้เมื่อไหร่" — อ่านคู่กันเสมอ
> อ่านคู่กับ: `CLAUDE.md` (กฎโปรเจกต์) · `SPEC.md` (ข้อกำหนด) · `task.md` (ความคืบหน้า + changelog) · `docs/แผนงานแก้ไข.md` (แผนรายข้อ A1–E1)

## 1. ทำไมต้องมีเอกสารนี้ (intent)

เจ้าของทำงานหลาย session พร้อมกัน แล้วเจอปัญหาจริง 2 อย่าง:

1. **ข้อมูลปนกัน** — `task.md` ชนกัน 2 ครั้ง เพราะหลาย session แก้ไฟล์เดียวกัน · `main` เคยเขียนว่า "โค้ดยังไม่เริ่ม" ทั้งที่อีก session ทำเสร็จไป 37 commit แล้ว
2. **session ไม่เข้าใจหน้าที่ตัวเอง** — session ชื่อ "Backend" แต่งานจริงคือรวมหน้า mockup

ทั้งสองอย่างมาจากสาเหตุเดียวกัน: **ไม่มีคนกลางถือภาพรวม และทุก session แก้ไฟล์ในพื้นที่เดียวกัน**

เอกสารนี้แก้ด้วย 3 หลัก:
- มี **ศูนย์กลาง (HQ)** หนึ่งเดียวที่ถือภาพรวม ตรวจงาน และรวมงาน
- แต่ละ session **มีพื้นที่ไฟล์ของตัวเอง** ไม่ทับกัน
- มี **แบบรายงานตายตัว** ทั้งขาเข้าและขาออก เพื่อให้ไม่มีใครต้องเดา

**เจ้าของไม่ใช่โปรแกรมเมอร์มืออาชีพ** (ทำงานแบบ vibe coding) จึงต้องการเข้าใจว่าระบบทำงานยังไง ไม่ใช่แค่ให้มันทำ — ทุกรายงานต้องอธิบายด้วยภาษาคน และบอกเหตุผลของขั้นตอน

## 2. เป้าหมาย / ไม่ใช่เป้าหมาย

**เป้าหมาย (goals)**
- เปิดงาน frontend, backend, database พร้อมกันได้โดยไม่ชนกัน
- เจ้าของแก้ mockup ได้บ่อยเท่าที่ต้องการ โดยไม่ทำให้งานอื่นพัง
- เปิด session ใหม่แล้ว session นั้นรู้หน้าที่ตัวเองทันทีจาก brief ไม่ต้องเดา
- ทุกเช้าเจ้าของเปิด HQ แล้วรู้สถานะโครงการใน 1–2 นาที
- ค่าใช้จ่ายระบบตอน production ไม่สูง (ไม่ใช่ค่า token)

**ไม่ใช่เป้าหมาย (non-goals)**
- ไม่ทำระบบ CI/CD เต็มรูปแบบในรอบนี้ (ตรวจอัตโนมัติตอน push อยู่ในหมวด 3 แยกต่างหาก)
- ไม่เปลี่ยนวิธีที่เจ้าของคุยกับ session mockup — ยังคุยตรงได้เหมือนเดิม
- ไม่บังคับให้ทุกคำสั่งผ่าน HQ

**สิ่งที่ถือว่าล้มเหลว (anti-goals)**
- เจ้าของต้องรอ HQ ตรวจนานจนแก้ mockup ไม่ทันใจ
- ขั้นตอนเยอะจนเจ้าของเลิกใช้แล้วกลับไปแก้ `main` ตรงๆ
- HQ รายงานว่า "เสร็จแล้ว" ทั้งที่ไม่ได้ตรวจของจริง (= หลอนซ้ำรอยเดิม)

## 3. ผังการทำงาน (เจ้าของอนุมัติแล้ว)

```
                    คุณ (เจ้าของ)
                   /            \
                  /              \  (คุยตรงได้ เพราะแก้บ่อย)
                 v                v
        ┌────────────────────┐   │
        │  HQ (session นี้)   │   │
        │ วางแผน ตรวจ รวม push│   │
        └─┬────┬────┬────┬───┘   │
          │    │    │    │       │
          v    v    v    v       │
        FE   DB   BE   หน้าจอจริง <┘
      mockup supabase lib,api  app,components
          │    │    │    │
          └────┴────┴────┴──> HQ ตรวจ ──> main
```

- **เจ้าของมี 2 เส้น**: คุยกับ HQ (วางแผน ตัดสินใจ) และคุยกับ session ลงมือตรงๆ
- **HQ เป็นคนเดียวที่รวมงานเข้า `main` และ push**
- ตัวหนังสือใต้ชื่อ session = **โฟลเดอร์เดียวที่ session นั้นแก้ได้**

### แมปผังกับ 5 หมวดใน `docs/แบ่งงาน-5-หมวด.md`

ผังด้านบนวาด 4 กล่องตอนคุยกัน แต่ไฟล์แบ่งงานมี 5 หมวด ใช้ **5 หมวดเป็นหลัก** (ละเอียดกว่า):

| กล่องในผัง | หมวดในไฟล์แบ่งงาน |
|---|---|
| Mockup + หน้าจอจริง | หมวด 1 — FE |
| Backend | หมวด 2 — BE |
| Database | หมวด 3 — INFRA (ส่วน migration/Supabase) |
| (ไม่มีในผัง) | หมวด 4 — DATA (สูตร snapshot, ส่ง Dashboard) |
| (ไม่มีในผัง) | หมวด 5 — DOC (SPEC, DECISIONS) |

**การตัดสินของผู้เขียน (เจ้าของตรวจได้):** ไม่แยก session "Database" ออกจาก INFRA เพราะงาน schema เหลือน้อยแล้ว (16 migration อยู่ใน `main` แล้ว) เหลือแค่รัน migration ขึ้น cloud + migration ใหม่ตาม SPEC §14 ข้อ 15–17

## 4. พื้นที่ไฟล์ของแต่ละ session (กฎกันชนกัน)

**กฎข้อเดียวที่สำคัญที่สุด: 2 session ห้ามแตะไฟล์เดียวกันพร้อมกัน**

| หมวด | แตะได้ | ห้ามแตะ |
|---|---|---|
| FE (mockup) | `docs/mockup/**` | ทุกอย่างนอกนั้น |
| FE (หน้าจอจริง) | `app/**`, `components/**`, `app/globals.css` | `lib/**`, `supabase/**` |
| BE | `lib/auth/**`, `lib/db/**`, `middleware.ts`, `app/(auth)/**` | `docs/mockup/**`, `app/(app)/**` |
| INFRA | `supabase/**`, `.github/**`, `vercel.json` | `app/**`, `components/**` |
| DATA | `lib/rules/**`, `lib/dashboard/**`, `lib/import/**`, `app/api/**` | `components/**`, `docs/mockup/**` |
| DOC | `SPEC.md`, `docs/DECISIONS.md`, `docs/*.md` | `task.md`, โค้ดทุกไฟล์ |

### เมื่อพื้นที่ทับกัน ใครเป็นเจ้าของ (ผู้เขียนตัดสิน)

ตารางด้านบนเป็น **ค่าเริ่มต้น** กฎตัดสินเมื่อทับกัน เรียงตามลำดับ:

1. **รายชื่อไฟล์ใน brief ชนะตาราง** — HQ เขียนรายชื่อไฟล์ที่แตะได้ลง brief ทุกครั้ง และเช็กลิสต์ข้อ 5.3 ตรวจเทียบกับ brief ไม่ใช่ตาราง
2. **path ที่เจาะจงกว่าชนะ path ที่กว้างกว่า:**
   - `app/(auth)/**` และ `middleware.ts` = BE (แม้ FE ได้ `app/**`)
   - `app/api/**` = DATA
   - `components/history/**` = BE (ลิ้นชักประวัติของจริงต้องอ่านข้อมูลตามสิทธิ์)
   - `supabase/tests/**` = ใครเขียน migration หรือตรวจ RLS รอบนั้น (ระบุใน brief)
   - หน้าปิดเดือน `app/(app)/closure/**` = FE ทำหน้าตา · DATA ส่งฟังก์ชันคำนวณใน `lib/**` ให้เรียก
3. **ไฟล์ที่ 2 หมวดต้องแก้จริง ให้ทำทีละหมวด ไม่ทำพร้อมกัน** — เช่น `app/(app)/layout.tsx`: FE ทำโครงหน้าก่อน → HQ รวม → BE ค่อยเติมการกันสิทธิ์ · ทางที่ดีกว่าคือ BE เขียนฟังก์ชันไว้ใน `lib/auth/**` แล้วให้ FE เรียกบรรทัดเดียว
4. HQ **ห้ามเปิด 2 session ที่ brief มีไฟล์ซ้ำกัน** ในเวลาเดียวกัน

### ไฟล์กลางที่ HQ แก้คนเดียว

**`task.md` · `CLAUDE.md` · `docs/แผนงานแก้ไข.md` · `docs/แบ่งงาน-5-หมวด.md`**

session อื่นห้ามแตะ — ให้ส่งรายงานมาแล้ว HQ เป็นคนลง เหตุผล: ไฟล์พวกนี้ทุก session อยากเขียน จึงชนกันบ่อยสุด (เคยชนมาแล้ว 2 ครั้ง)

**ข้อยกเว้น:** `SPEC.md` ให้หมวด DOC แก้ได้ แต่ **ต้องไม่มี session อื่นทำงาน DOC พร้อมกัน** (เปิดได้ทีละ 1)

## 5. ขั้นตอนส่งงาน ตรวจ และรวมเข้า main

เจ้าของยืนยันแล้วว่า **รับได้ที่ต้องรอ HQ ตรวจก่อนงานเข้า `main`**

### 5.1 session ลงมือทำงานที่ไหน

**ใช้ worktree แยกต่อ session** (พื้นที่ทำงานแยกคนละโฟลเดอร์ บน branch ของตัวเอง)

- HQ เปิด session ด้วย `use_worktree: true` ทุกครั้งที่ session นั้นจะ **เขียนโค้ด**
- ข้อดี: แก้ไฟล์ชนกันไม่ได้เลยแม้แตะไฟล์เดียวกัน · `main` ไม่พังระหว่างทาง · ย้อนกลับง่าย
- ข้อแลก: งานของ session นั้น **ไม่อยู่ใน `main`** จนกว่า HQ จะรวม

**ข้อยกเว้น:** session mockup ที่เจ้าของคุยตรงและอยากเห็นผลทันที ใช้โฟลเดอร์เดียวกับ `main` ได้ (`use_worktree: false`) เพราะแตะแค่ `docs/mockup/**` ซึ่งไม่มีใครอื่นแตะ — **แต่เปิดได้ทีละ 1 ตัวเท่านั้น** (sub session ของมันต้องแบ่งคนละไฟล์ตามกฎ `CLAUDE.md`)

**mockup เข้า `main` ยังไง (ผู้เขียนตัดสิน):** session mockup **commit ลง `main` ในเครื่องได้เลย** เจ้าของจึงเห็นผลทันทีไม่ต้องรอ · **ด่านตรวจของ mockup คือตอน push** — HQ ตรวจตามเช็กลิสต์ 5.3 (เบราว์เซอร์ สว่าง/มืด/375px) ก่อน push ทุกครั้ง · mockup เป็นไฟล์ตัวอย่าง ไม่ต่อฐานข้อมูล พังแล้วไม่กระทบผู้ใช้ จึงยอมให้ตรวจย้อนหลังได้ ส่วน **โค้ดจริงทุกหมวดต้องตรวจก่อนเข้า `main` เสมอ**

**HQ ทำงานในโฟลเดอร์เดียวกับ mockup:** HQ แตะเฉพาะไฟล์กลาง (ไม่แตะ `docs/mockup/**`) และ stage ด้วยชื่อไฟล์ทุกครั้ง · ก่อน merge งานจาก worktree เข้า `main` HQ ต้องดู `git status` ก่อน ถ้า mockup มีไฟล์แก้ค้าง ให้รอ session mockup commit ก่อน

**เจ้าของคุยตรงกับ session ไหนก็ได้** ไม่จำกัดแค่ mockup — เส้นคุยตรงในผังหมายถึงทุก session ลงมือ · สิ่งที่ต้องผ่าน HQ มีแค่ การรวมเข้า `main` (โค้ดจริง), การ push และการแก้ไฟล์กลาง

### 5.2 ขั้นตอนเมื่อ session ทำเสร็จ

1. session **commit เอง** ด้วย `git add <ชื่อไฟล์>` ระบุทีละไฟล์ — **ห้าม `git add -A` หรือ `git add .`** (กันเก็บงานค้างของคนอื่น)
2. session **ห้าม push** และ **ห้าม merge เข้า `main`** เอง
3. session ส่ง **รายงานจบงาน** (แบบในข้อ 6.1) มาที่ HQ
4. HQ **ตรวจของจริง** ตามเช็กลิสต์ข้อ 5.3 — ไม่เชื่อรายงานอย่างเดียว
5. HQ รวมเข้า `main` แล้วรายงานเจ้าของ
6. HQ **push เมื่อเจ้าของยืนยัน** เท่านั้น

### 5.3 เช็กลิสต์ที่ HQ ต้องทำก่อนรวมงาน (ห้ามข้าม)

- [ ] `git diff` ดูว่าแตะเฉพาะไฟล์ในพื้นที่ของตัวเอง ไม่มีไฟล์แปลกปลอม
- [ ] ไม่มีคีย์ลับ / ไฟล์ `fixtures/` หลุดเข้า commit
- [ ] งานโค้ด: รัน `npm run typecheck` + `npm run lint` + `npm test` เอง — **ไม่เชื่อตัวเลขในรายงาน**
- [ ] งาน mockup: เปิดในเบราว์เซอร์จริง ทั้งโหมดสว่าง/มืด และจอ 375px · ไม่มี console error
- [ ] งาน schema: รัน `npm run db:test` เอง (ต้องเปิด Docker)
- [ ] ถ้าเป็น worktree: `git merge` เข้า `main` แล้วแก้ conflict ที่ไฟล์กลางโดย **เก็บของทั้งสองฝั่ง** ไม่ทิ้งของใคร

**ถ้าข้อไหนไม่ผ่าน:** ห้ามรวม · ห้ามเปลี่ยนชื่อ session เป็น `Done_` · บอกเจ้าของตามจริงว่าติดอะไร

## 6. แบบรายงาน (ตายตัว ใช้ทุกครั้ง)

### 6.1 รายงานจบงาน: session → HQ

```
เสร็จ: <ชื่องาน>
branch: <ชื่อ branch> · commit: <hash>
ไฟล์ที่แตะ: <รายชื่อ>
ตรวจแล้ว: typecheck ✅/❌ · lint ✅/❌ · test <n> ผ่าน · เบราว์เซอร์ ✅/❌
phase ที่ขยับ: phase <n> จาก <x>% เป็น <y>% (ประมาณ)
ทำไม่ได้ / ยังค้าง: <รายการ หรือ "ไม่มี">
ต้องให้เจ้าของตัดสิน: <รายการ หรือ "ไม่มี">
กระทบ session อื่น: <เช่น "เพิ่มช่องข้อมูลใหม่ ต้องแจ้ง DB" หรือ "ไม่มี">
```

บรรทัด "phase ที่ขยับ" บังคับ เพราะ `CLAUDE.md` กำหนดว่า sub session ไม่แก้ตารางความคืบหน้าเอง — HQ เป็นคนลงให้

**ส่งทางไหน (ผู้เขียนตัดสิน):**
- session ที่ **HQ เป็นคนเปิด**: จบงานแล้วพิมพ์รายงานเป็นข้อความสุดท้าย แอปจะแจ้ง HQ เองเมื่อ session นั้นจบรอบ HQ อ่านรายงานเต็มจาก session นั้น — เจ้าของไม่ต้อง copy
- session ที่ **เจ้าของเปิดเอง** (เช่น mockup): เจ้าของบอก HQ ประโยคเดียวว่า "session X เสร็จแล้ว" HQ ไปอ่านรายงานจาก session นั้นเอง
- **ไม่เขียนรายงานลงไฟล์ใน repo** — กันไฟล์ชนกัน

### 6.2 รายงานเช้า: HQ → เจ้าของ

**เกิดเมื่อไหร่ (ผู้เขียนตัดสิน):** เมื่อเจ้าของพิมพ์ว่า "รายงานเช้า" ใน HQ — ไม่ตั้งเวลาอัตโนมัติในรอบนี้ (ตั้งทีหลังได้ถ้าเจ้าของต้องการ) · ก่อนรายงาน HQ ต้องดู git และรายการ session จริงทุกครั้ง ไม่ตอบจากความจำ

เจ้าของขอ 4 อย่าง อ่านจบใน 1–2 นาที:

```
## 1. ความคืบหน้า
รวม <n>% · phase ไหนขยับจากเมื่อวาน

## 2. งาน
เสร็จเมื่อวาน: <สั้นๆ>
กำลังทำ: <session ไหน ทำอะไร>
วันนี้ควรทำ: <1–3 ข้อ เรียงตามความสำคัญ>
ติดรอเจ้าของ: <รายการ>

## 3. อธิบายขั้นที่กำลังจะทำ (สำหรับมือใหม่)
<ขั้นนี้คืออะไร ทำไปทำไม ถ้าไม่ทำจะเป็นยังไง — ภาษาคน ไม่เกิน 4–5 บรรทัด>

## 4. มาตรฐานสากล
<วิธีที่เรากำลังทำตรงกับที่ทีมพัฒนาทั่วไปทำไหม ตรงไหนควรปรับ — 2–3 บรรทัด ผูกกับงานวันนั้น>
```

## 8. แบบ brief สำหรับเปิด session ใหม่

ทุก brief มี 5 หัวข้อนี้ **ครบทุกครั้ง** ขาดข้อไหนคือต้นเหตุของ "session ไม่รู้หน้าที่ตัวเอง"

```
1. งานนี้คืออะไร (1–3 บรรทัด + หมวด FE/BE/INFRA/DATA/DOC)
2. อ่านก่อน: CLAUDE.md · docs/แบ่งงาน-5-หมวด.md (หมวดของตัวเอง) · <ไฟล์เฉพาะงาน>
3. แตะได้เฉพาะ: <รายชื่อไฟล์/โฟลเดอร์>   ห้ามแตะ: task.md, CLAUDE.md, ไฟล์ของหมวดอื่น
4. เสร็จ = <เกณฑ์วัดได้ เช่น "typecheck+lint ผ่าน · เปิด 375px ไม่ล้น · ไม่มี console error">
5. ข้อห้าม: ห้าม push · ห้าม merge เข้า main · ห้าม git add -A · จบงานส่งรายงานตามแบบข้อ 6.1
```

**ชื่อ session บอกสถานะเสมอ (กฎเดิมใน `CLAUDE.md` — เจ้าของยืนยันซ้ำ 10 พ.ย. 2026 ว่าใช้เหมือนเดิม):**

| จังหวะ | ชื่อ session |
|---|---|
| เสนอเป็นการ์ด ยังไม่เริ่ม | `<ชื่องาน>` เฉยๆ |
| เริ่มทำแล้ว | `กำลังทำ_<ชื่องาน>` |
| session รายงานว่าเสร็จ | `Done_<ชื่องาน>` |

- HQ (หรือ session หมวดแม่) เป็นคนเปลี่ยนชื่อให้ทันทีที่สถานะเปลี่ยน เจ้าของดูแถบ session แล้วรู้เลยโดยไม่ต้องกดเข้าไป
- **งานไม่สำเร็จ / ติดปัญหา ห้ามใส่ `Done_`** — คงชื่อ `กำลังทำ_` ไว้ แล้วบอกเจ้าของว่าติดอะไร
- ถ้า HQ ตรวจงานที่ขึ้น `Done_` แล้วพบว่า **ไม่ผ่าน** (เช็กลิสต์ 5.3) ให้เปลี่ยนชื่อกลับเป็น `กำลังทำ_` และบอกเจ้าของ — `Done_` จึงแปลว่า "session บอกว่าเสร็จ" ส่วน "ตรวจผ่านและรวมแล้ว" ดูได้จากหัวข้อ "งานรอตรวจ" ใน `task.md`
- ชื่องานใส่ตัวย่อหมวดนำหน้า: `FE` · `BE` · `INFRA` · `DATA` · `DOC` เช่น `กำลังทำ_FE_ชิ้นส่วนกลาง`

### โมเดลที่ใช้ (ลดค่าใช้จ่าย token)

ตามตารางใน `CLAUDE.md` — หลักคือ **งานเสี่ยงต่อความถูกต้อง/ข้อมูลลูกค้า ใช้ Opus · งานตามแพทเทิร์นใช้ Sonnet**

| หมวด | โมเดล | เหตุผล |
|---|---|---|
| FE | Sonnet | ทำตาม mockup ที่อนุมัติแล้ว |
| BE | **Opus** | พลาด = ข้อมูลลูกค้ารั่ว (PDPA) |
| INFRA (ตั้งค่า CI, Vercel, รัน migration ที่มีอยู่) | Sonnet | งานตั้งค่าตามขั้นตอน |
| INFRA (**เขียน migration ใหม่ / RLS / สิทธิ์**) | **Opus** | กฎ `CLAUDE.md`: schema และสิทธิ์แตะข้อมูลลูกค้า (PDPA) — แยกเป็น session ของตัวเอง |
| DATA | **Opus** | สูตรผิด = ตัวเลขผู้บริหารผิด |
| DOC | Sonnet | งานเขียน |

**ใครเลือกโมเดล (เจ้าของตัดสิน 10 พ.ย. 2026):** **เลือกโมเดลตอนเปิด sub session ทีละงาน** — งานยากเปิดด้วย Opus งานตามแบบเปิดด้วย Sonnet · เมื่อ HQ (หรือ session หมวด) เป็นคนเปิด sub session ให้กำหนดโมเดลตามตารางนี้ได้เลยโดยไม่ต้องถามทุกครั้ง แต่ต้องบอกเจ้าของในบรรทัดเดียวว่าเลือกอะไรเพราะอะไร · **ไม่สลับโมเดลกลาง session** (รอบถัดไปต้องอ่านบทสนทนาใหม่ทั้งหมด เปลืองกว่าที่ประหยัด) · โมเดลของ session ที่เจ้าของเปิดเอง (HQ และ 5 หมวด) เจ้าของยังเป็นคนเลือก

### session ที่มีอยู่จริง (เจ้าของสร้างไว้ 10 พ.ย. 2026 — ตรวจจากรายการ session แล้ว)

| session | หน้าที่ |
|---|---|
| `Fable_ศูนย์กลางสั่งงานทั้ง project` | HQ |

- คำนำหน้าชื่อของ session ประจำ 5 หมวด (ตามที่เจ้าของตั้งไว้): `ยังไม่มีงาน_` เมื่อว่าง · `กำลังทำ_` เมื่อมีงานเดินอยู่ (ตัวมันเองหรือ sub session ของมัน) · HQ เปลี่ยนชื่อให้ตรงสถานะจริงทุกครั้งที่ตรวจพบว่าไม่ตรง · sub session ใช้ `กำลังทำ_` / `Done_` ตามกฎข้อ 8
- **ทั้ง 5 หมวดเปิดในโฟลเดอร์เดียวกับ `main`** (ไม่ใช่ worktree) → session หมวดทำหน้าที่ **คุมงานของหมวด** ส่วนการเขียนโค้ดจริงให้แตกเป็น sub session ใน worktree แยกตามข้อ 5.1 · ถ้าหมวดไหนแก้ไฟล์เองในโฟลเดอร์ `main` ต้องอยู่ในพื้นที่ไฟล์ของหมวดและ stage ด้วยชื่อไฟล์เท่านั้น
- แอปแจ้ง HQ อัตโนมัติเฉพาะ session ที่ HQ เปิดเอง → งานของ 5 หมวด เจ้าของบอก HQ ว่า "หมวด N เสร็จ" แล้ว HQ เข้าไปอ่านรายงานเอง (ข้อ 6.1)

### หน้าจอจริงเริ่มได้เมื่อไหร่ (เจ้าของตัดสิน 10 พ.ย. 2026)
