# คู่มือกู้คืนข้อมูล (จากไฟล์สำรองใน Cloudflare R2)

> ใช้เมื่อ: ข้อมูลพัง / ถูกลบผิด / Supabase มีปัญหา · และใช้ **ซ้อมกู้เดือนละครั้ง** (สำรองที่ไม่เคยซ้อมกู้ = เชื่อไม่ได้)
> เป้าหมาย: เสียข้อมูลไม่เกิน 1 วัน · กู้เสร็จภายในครึ่งวัน
> ที่มา: `docs/plans/2026-11-14-backup-and-usage-monitoring.md` · DECISIONS 2.33

**หลักการ: กู้ลง "ฐานข้อมูลในเครื่อง" ก่อนเสมอ → ตรวจตัวเลข → ค่อยตัดสินใจเรื่อง cloud (เฉพาะเจ้าของสั่ง)**
สคริปต์กู้คืน (`restore-local.sh`) ถูกออกแบบให้ **ปฏิเสธทำงานถ้าเป้าหมายไม่ใช่เครื่องตัวเอง** จึงกู้ทับ cloud โดยไม่ตั้งใจไม่ได้

## ของที่ต้องมี

| ของ | อยู่ที่ไหน |
|---|---|
| ไฟล์สำรอง `db-YYYY-MM-DD.tar.age` | Cloudflare R2 bucket (โฟลเดอร์ `daily/` `weekly/` `monthly/`) |
| **private key ของ age** (ไฟล์ `aga-backup-key.txt`) | ตัวจัดการรหัสผ่านของเจ้าของ — ⚠ ถ้าไม่มี กู้ไม่ได้ |
| repo สำรอง `AGA-Bait-Registry-backup` (มี `scripts/restore-local.sh`) | `C:\Users\advan\Claude_Cowork\AGA-Bait-Registry-backup` |
| Docker Desktop เปิดอยู่ + Supabase local รันอยู่ | ในเครื่อง |
| โค้ด repo หลักที่ **commit ตรงกับวันที่สำรอง** | `git log` หา commit ของวันนั้น (โครงสร้างตารางมาจาก migration ของ repo) |

## ขั้นที่ 1 — ดาวน์โหลดไฟล์สำรอง

เลือกวิธีที่ง่ายกว่า:

- **หน้าเว็บ (ง่ายสุด):** Cloudflare → R2 → bucket → โฟลเดอร์ `daily/` → กดไฟล์วันที่ต้องการ → **Download**
  (วางไว้ที่ `C:\Users\advan\Claude_Cowork\restore-work\` — โฟลเดอร์นี้อยู่นอกโปรเจกต์ ห้ามนำเข้า git)
- หรือใช้ rclone: ให้ศูนย์กลางทำให้ (ต้องตั้ง rclone ด้วย key ของ R2 ซึ่งเจ้าของไม่ต้องส่งให้ใคร)

เลือกวันไหน: ข้อมูลพังเมื่อวาน → ใช้ไฟล์ของ **เมื่อวานหรือก่อนหน้า** (ไฟล์วันนี้อาจมีข้อมูลที่พังแล้ว) · ไม่แน่ใจ → ใช้ `weekly/` หรือ `monthly/` ก่อนเพื่อหาว่าพังตั้งแต่เมื่อไหร่

## ขั้นที่ 2 — เตรียมฐานข้อมูลในเครื่องให้สะอาด

เปิดโฟลเดอร์ repo หลัก (ที่ checkout ตรงกับวันที่สำรอง) ในเทอร์มินัล แล้วรัน:

```bash
npx supabase db reset --local
```

> ⚠ คำสั่งนี้ **ล้างฐานข้อมูลในเครื่อง** (ไม่เกี่ยวกับ cloud) — ฐานข้อมูลในเครื่องมีตัวเดียวใช้ร่วมกันทุก session ให้แจ้งศูนย์กลางก่อนรัน

## ขั้นที่ 3 — ถอดรหัส + กู้ + นับแถว (ทำในขั้นเดียว)

สคริปต์จะ: ถอดรหัสด้วย private key → ล้างตารางข้อมูลในเครื่อง → กู้ข้อมูล `auth` + `storage` + `public` → **นับแถวทุกตารางเทียบกับตัวเลขตอนสำรอง**

วางไฟล์สำรอง + ไฟล์กุญแจ `aga-backup-key.txt` ไว้ใน `C:\Users\advan\Claude_Cowork\restore-work\` แล้วรัน (ผ่าน Docker เพื่อไม่ต้องติดตั้งเครื่องมือเพิ่ม):

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v "C:/Users/advan/Claude_Cowork/AGA-Bait-Registry-backup:/repo:ro" -v "C:/Users/advan/Claude_Cowork/restore-work:/in" -e AGE_IDENTITY_FILE=/in/aga-backup-key.txt -e RESTORE_DATABASE_URL="postgresql://supabase_admin:postgres@host.docker.internal:54322/postgres" ubuntu:24.04 bash -c "/repo/scripts/install-tools.sh >/dev/null && /repo/scripts/restore-local.sh /in/db-2026-11-14.tar.age"
```

(เปลี่ยน `db-2026-11-14.tar.age` ในคำสั่งเป็นชื่อไฟล์ที่ดาวน์โหลดมา)

**ผลที่ถูกต้อง** ลงท้ายด้วย:

```
นับแถวเทียบ manifest
ตรง: 27 ตาราง · รวม NNN แถว
```

ถ้าขึ้น **"ไม่ตรง!"** พร้อมรายการตารางที่ต่าง → **หยุด อย่าไปต่อ** แจ้งศูนย์กลาง (อาจต่างได้ 1–2 แถวถ้ามีคนกรอกข้อมูลตอนสำรอง · ต่างมากกว่านั้นผิดปกติ)

> ตัวเลข "รวม NNN แถว" ที่ถูกต้องคือตัวเลขในรายงานของงานสำรองครั้งนั้น · ตอนทดสอบระบบด้วยข้อมูลสมมติได้ 27 ตาราง / 205 แถว

## ขั้นที่ 4 — ตรวจด้วยตา (ข้อมูลจริงอ่านได้)

1. รัน `npm run dev` แล้วเปิดแอป (ฐานข้อมูลในเครื่อง)
2. ล็อกอินด้วยผู้ใช้จริง (ผู้ใช้กู้มาด้วย) → เปิดหน้าลูกค้า/สัญญา เลือกลูกค้า 2–3 ราย เทียบกับที่รู้ว่าถูกต้อง
3. ตรวจจำนวนสัญญาและมูลค่ารวม ว่าตรงกับรายงานล่าสุดที่เจ้าของจำได้
4. ไฟล์ PDF: ไฟล์ที่เข้ารหัสอยู่ที่ `files/` ใน R2 (ถอดรหัสทีละไฟล์ด้วย `age -d -i <key> <ไฟล์>`) — ตอนซ้อมกู้ไม่ต้องกู้ PDF ทุกไฟล์ ลองถอดรหัส 1–2 ไฟล์ให้เปิดอ่านได้ก็พอ

## ขั้นที่ 5 — (เฉพาะกรณีจริง) กู้ขึ้น cloud

**ห้ามทำเอง ห้ามให้ session ใดทำ จนกว่าเจ้าของสั่งเป็นข้อความชัดเจน** เพราะเป็นการเขียนทับข้อมูลจริง
เมื่อเจ้าของสั่ง ศูนย์กลางจะเสนอวิธีที่ปลอดภัย (เช่น สร้างโปรเจกต์ Supabase ใหม่ กู้ลงโปรเจกต์ใหม่ ตรวจ แล้วค่อยสลับ — แทนการเขียนทับโปรเจกต์เดิม) พร้อมสรุปความเสี่ยงให้ตัดสินใจ

## ซ้อมกู้รายเดือน (ศูนย์กลางทำ — ไม่แตะ cloud)

| ทำ | ผ่านเมื่อ |
|---|---|
| ทุกวันที่ 1–3 ของเดือน: ทำขั้น 1–3 ด้วยไฟล์ `daily/` ล่าสุด | ขึ้น "ตรง: ... ตาราง" |
| เปิดแอปในเครื่องดูข้อมูล 2–3 รายการ (ขั้น 4) | ข้อมูลอ่านได้ ตัวเลขสมเหตุสมผล |
| ถอดรหัส PDF 1–2 ไฟล์ | เปิดอ่านได้ |
| บันทึกผลลงรายงานประจำเดือน (วันที่ซ้อม · ไฟล์ที่ใช้ · จำนวนแถว · ผ่าน/ไม่ผ่าน) | — |
| เสร็จแล้ว `npx supabase db reset --local` คืนฐานข้อมูลในเครื่องให้สะอาด | — |

ถ้าซ้อมไม่ผ่านเมื่อไหร่ ให้ถือว่าการสำรองยังเชื่อไม่ได้ → แจ้งเจ้าของทันที

## ปัญหาที่พบบ่อย

| อาการ | สาเหตุ / ทางแก้ |
|---|---|
| `no identity matched any of the recipients` | ใช้ private key ผิดไฟล์ — ต้องเป็นคู่กับ public key ที่ตั้งไว้ใน GitHub (`AGE_RECIPIENT`) |
| `ปฏิเสธ: เป้าหมาย ... ไม่ใช่เครื่องตัวเอง` | ระบบกันไว้ถูกแล้ว — สคริปต์กู้ลง cloud ไม่ได้ (ตั้งใจ) |
| `connection refused` ที่พอร์ต 54322 | Supabase local ยังไม่รัน (`npx supabase start`) หรือ Docker Desktop ปิดอยู่ |
| ตารางไม่ตรงหลายตาราง | repo หลักไม่ตรงกับวันที่สำรอง (migration ต่างกัน) → checkout commit ของวันนั้นแล้วทำขั้น 2 ใหม่ |
