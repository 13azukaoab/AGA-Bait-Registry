## ข้อเท็จจริงที่เจอ (มีผลต่อแบบ)
- **`lib/rules` ไม่ต้องแก้** — `isMissedService` ใช้แค่ `contractId / visitDate / visitType` · snapshot ใช้แค่สัญญา · ไม่มีอะไรอ่านทีม เวลา หรือรายละเอียดสถานี → `dashboard_data.json` ไม่กระทบ
- `follow_up_no` ไม่ได้อยู่ใน `lib/rules` — คำนวณใน DB ด้วย trigger `set_follow_up_no` (BEFORE INSERT เท่านั้น) · **ช่องโหว่เดิม:** แก้วันที่ของ visit หรือลบ visit/ผลตรวจย้อนหลัง → เลข F ของรอบหลังๆ ไม่คำนวณใหม่ (ตอนนี้หัวหน้างานแก้/ลบย้อนหลังได้ — SPEC §7.7)
- **ทีม A–O, Z มีครบแล้ว** (seed เดิม + ทีม Sup) ไม่ต้องเพิ่ม
- **หัวหน้างาน (recorder) เขียน `stations` ไม่ได้เลย** — RLS ให้แค่ host / admin · แต่ v1.8 ให้หัวหน้างานสร้างสถานีเดือนแรก ฝังเพิ่ม และเปลี่ยนสถานะ (หาย/ถอน/รอถอด/ถอด) → ต้องเพิ่มสิทธิ์ (ข้อ 3 และค่าเริ่มต้นทางเทคนิค ข้อ 6)
- `stations.code` เป็นข้อความอิสระ ไม่มี unique · `station_checks` มี `termite_caste` (สัดส่วน 6 ค่าของ AG) + `bait_added_g` (หาร 50) เท่านั้น ไม่มีชนิดปลวกใต้ดิน/สวน เคมีผง ไม้ การกินเหยื่อ
- `visits` มียอดรวม `timber_pcs`, `bait_ig_ic_g`, `bait_ag_g`, `powder_chemical`, `duration_min` (ให้ผู้ใช้กรอกเอง) — v1.8 ต้องการรายละเอียดรายสถานีแทน
- mockup ฟอร์มมี 4 ตาราง: **พบปลวก** (เลขสถานี · IG/IC · ใต้ดิน = เหยื่อ ก. / สวน = เคมีผง จำนวนจุด) · **เปลี่ยนไม้ล่อ** (เลขสถานี · ไม้ IG 2 ชิ้น / IC 1 ชิ้น อัตโนมัติ) · **งานซ่อม/ฝังเพิ่ม** · **กล่อง AG**

## 1. ตาราง / คอลัมน์ / constraint

### 1.1 `visits` — เวลาเข้า–ออก + หลายทีม
- เพิ่ม `start_time time`, `end_time time` · CHECK `end_time > start_time` (ยังไม่รองรับข้ามเที่ยงคืนตาม SPEC)
- บังคับมีทั้ง 2 ช่องด้วย `NOT NULL` ตรงๆ — SPEC §10 ข้อ 4 **ไม่นำเข้าผลบริการย้อนหลัง** จึงไม่มีแถวเก่าที่ไม่มีเวลา (ไม่ใช้ CHECK แบบ `NOT VALID` เพราะยังบังคับตอน UPDATE แถวเก่าอยู่ดี) · ถ้าบน cloud มีแถว visits อยู่แล้ว migration จะหยุดเอง ไม่แก้ข้อมูลเงียบๆ · ไฟล์เทสเก่าที่สร้าง visits โดยไม่มีเวลาต้องเติมเวลา
- `duration_min` → ลบแล้วสร้างใหม่เป็น **generated** = นาทีระหว่าง end − start (ผู้ใช้กรอกไม่ได้ · SPEC "คำนวณเอง")
- ตารางใหม่ `visit_teams (visit_id → visits ON DELETE CASCADE, team_id → teams, PK คู่)` · ต้องมี ≥ 1 ทีม (ตรวจใน RPC — constraint ข้ามตารางทำไม่ได้)
- ย้ายข้อมูล: `INSERT INTO visit_teams SELECT id, team_id FROM visits WHERE team_id IS NOT NULL` แล้วลบ `visits.team_id` (ค่าเริ่มต้นทางเทคนิค ข้อ 6)

### 1.2 `stations` — เลขแยกชนิด + ป้ายจุด
- เพิ่ม `station_no int` (> 0) · ไม่ซ้ำต่อ (`contract_id`, `type`, `station_no`) → IG-5 กับ IC-5 อยู่ด้วยกันได้ · ถ้าเจ้าของให้ใช้เลขเดิมแทนสถานีที่หาย (ข้อ 6 ง) จะบังคับไม่ซ้ำ **เฉพาะสถานีที่ยังใช้งาน** (partial unique index) · `code` เดิมคงไว้แต่เลิกใช้ (แถวเก่าย้ายเลขจาก `code` ถ้าแปลงเป็นตัวเลขได้)
- เพิ่ม `point_label text` (ไม่บังคับ · ใช้กับ AG · จำข้ามเดือนเพราะอยู่ที่สถานี ไม่ใช่ที่ผลตรวจ)
- `contracts.stations_initialized_at timestamptz` — แยก "ยังไม่ระบุจำนวนสถานี" ออกจาก "ระบุแล้วว่า IC = 0" (ถ้าดูแค่จำนวนแถวจะแยกไม่ได้)
- ฝังเพิ่ม: เลขใหม่ต้อง > **จำนวนเดิมของชนิดนั้น** และไม่ซ้ำ (DECISIONS 2.15) — ตรวจใน RPC · unique กันซ้ำระดับฐานข้อมูลอีกชั้น
- หาย / ถอนออก = เปลี่ยน `status` (ไม่ลบแถว) · **สถานะที่ใช้ให้เจ้าของเลือก (ข้อ 5 ง)** เพราะติดคำถามเดิม X2 (`eliminated` / `pending_removal` ยังไม่นิยาม) และ `removed` ตอนนี้แปลว่า "ถอดกล่อง AG = จบปัญหา" (§7.5) + ใช้ในการเก็บสถานีคืน (§7.8) — เอา "ถอนออกกลางสัญญา" ไปรวมจะทำให้ตัวเลข 2 เรื่องนี้เพี้ยน
- ถ้าต้องเพิ่มค่าใน enum (`ALTER TYPE … ADD VALUE`) แยกเป็น migration ไฟล์ของตัวเอง ก่อนไฟล์ที่ใช้ค่านั้น (ใช้ค่าใหม่ใน transaction เดียวกับที่เพิ่มไม่ได้)

### 1.3 `station_checks` — ผลตรวจรายสถานี
- `bait_added_g`: CHECK เดิม (หาร 50) + เพิ่มช่วง 0–5,000 (SPEC: เกิน 200 พิมพ์เองได้)
- เพิ่ม `bait_eaten_pct smallint` CHECK IN (0, 25, 50, 75, 100) · ไม่บังคับ
- เพิ่ม `termite_group` enum (`subterranean` ใต้ดิน / `garden` สวน) สำหรับ IG/IC ที่พบปลวก · `powder_points int` (เคมีผง — ใช้กับ `garden` เท่านั้น · กรัม = จุด × 0.3 คำนวณตอนสรุป ไม่เก็บ)
- เพิ่ม `timber_replaced boolean` (เปลี่ยนไม้ล่อ · จำนวนชิ้นคำนวณตอนสรุปจากชนิด: IG 2 / IC 1 — ไม่เก็บตัวเลขซ้ำ)
- เพิ่ม `checked boolean NOT NULL DEFAULT true` — **"ไม่ได้ตรวจจุดนี้"** (ข้อ **ข**)
- CHECK สอดคล้องกัน: ไม่ได้ตรวจ → ห้ามมีผล · `garden` → ห้ามมีเหยื่อ · `subterranean` → ห้ามมีเคมีผง
- 1 สถานีมีผลได้ 1 แถวต่อการเข้า 1 ครั้ง: UNIQUE (`visit_id`, `station_id`)

### 1.4 งานซ่อม / ฝังเพิ่ม — ตารางใหม่ `station_works`
`(id, visit_id → visits CASCADE, kind, station_type IG|IC, station_nos int[], detail text, created_by, created_at)`
- `kind` enum: `cap_replaced` เปลี่ยนฝา · `lost` สถานีหาย · `withdrawn` ถอนออก · `other` อื่นๆ · `added` ฝังใหม่
- `station_nos` = เลขที่แปลงจาก "3, 5, 8-12" แล้ว (เก็บเป็นเลขจริง ค้นประวัติของสถานีได้ด้วย index GIN)
- CHECK: `lost` / `other` ต้องมี `detail` · `station_nos` ไม่ว่าง ไม่มีเลขซ้ำ
- ผลต่อ `stations` (ทำใน RPC transaction เดียวกัน): `lost` → status `lost` · `withdrawn` → `removed` + `removed_at` · `added` → สร้างแถวใหม่ · `cap_replaced` / `other` → ไม่เปลี่ยนจำนวน
- แปลงข้อความช่วงเลขเป็นตัวเลข: ทำที่หน้าจอ (แสดงผลสด) **และ** ตรวจซ้ำใน RPC · เสนอ pure function `lib/service/stationNumbers.ts` + unit test ให้ FE ใช้ร่วม (ไม่ใช่ `lib/rules`)

### 1.5 สรุปเวลาทำงาน / วัสดุ — view (ไม่เก็บซ้ำ)
- `v_visit_team_minutes` = visit × ทีม × `duration_min` (หลายทีม = นับเต็มทุกทีม — DECISIONS 2.14)
- `v_service_materials` = ต่อ visit: เหยื่อนอก (IG+IC) · เหยื่อใน (AG) · เคมีผง (จุด) · ไม้ (IG×2 + IC×1)
- ทั้งคู่ `security_invoker = true` (RLS ของตารางต้นทางทำงาน) · ไม่ GRANT ให้ anon
- ยอดรวมเดิมใน `visits` (`timber_pcs`, `bait_ig_ic_g`, `bait_ag_g`, `powder_chemical`) → เลิกใช้ (ข้อ **ก**)

## 2. `follow_up_no` (F1–F10)
- นับ **เฉพาะแถวที่ `checked = true`** · แถว "ไม่ได้ตรวจ" ได้ `follow_up_no = NULL` และไม่ทำให้เลขของรอบถัดไปขยับ
- กติกาเดิมคงไว้: นับต่อสถานี · วันเดียวกันได้เลขเดียวกัน · คำนวณเองเสมอ (ผู้ใช้ส่งมาก็ถูกทับ)
- **แก้ช่องโหว่เดิม (ค่าเริ่มต้นทางเทคนิค ข้อ 6):** คำนวณเลขใหม่ทั้งสถานีเมื่อ แก้ `visit_date` / ลบ visit / ลบหรือเปลี่ยน `checked` ของผลตรวจ — ไม่งั้นแก้ย้อนหลัง (ซึ่งอนุญาตตาม §7.7) แล้ว F ผิด
- ใช้กับทุกชนิดสถานี (IG/IC ก็มีเลข แต่หน้าจอโชว์ F เฉพาะ AG ตาม §7.5)

## 3. สิทธิ์ (RLS) + audit
| ตาราง | host | recorder (ในขอบเขต) | admin | viewer / anon |
|---|---|---|---|---|
| `visits`, `visit_teams`, `station_checks`, `station_works` | ทั้งหมด | เพิ่ม/แก้/ลบ | อ่าน | ไม่มีสิทธิ์ (PDPA) |
| `stations` | ทั้งหมด | **เพิ่ม + เปลี่ยนสถานะ/ป้ายจุด** (ค่าเริ่มต้นทางเทคนิค ข้อ 6) | เพิ่ม/แก้/ลบ (เดิม) | ไม่มีสิทธิ์ |
| view สรุปเวลา/วัสดุ | อ่าน | อ่าน | อ่าน | ไม่มีสิทธิ์ |
- ทุกตารางใหม่: RLS เปิด · GRANT ในไฟล์เดียวกัน · REVOKE จาก anon ตรงตัว
- audit: `visit_teams`, `station_works` ใส่ trigger audit (แก้/ลบลง `audit_log` · **เพิ่มไม่ลง** ตาม M3 เหมือน visits/station_checks) · ต้องสอน `audit_trigger()` ให้รู้จักตารางใหม่ (หา `branch_id` / `contract_id` / `month_key` ผ่าน visit) ด้วย `CREATE OR REPLACE` ใน migration ใหม่

## 4. แก้ / ลบผลบริการที่บันทึกแล้ว (หัวหน้างานแก้ย้อนหลังได้ — §7.7)
- **ไม่ลบทั้งชุดแล้วใส่ใหม่** — เพราะ M3 เลิกเก็บ audit ของการ "เพิ่ม" ใน visits / station_checks และ "ใครกรอกเมื่อไหร่" อ่านจาก `created_by` / `created_at` (DECISIONS 4.3): ลบแล้วใส่ใหม่ = ประวัติเห็นแต่การลบ ไม่เห็นค่าเดิม→ค่าใหม่ · `created_by` กลายเป็นคนแก้ · จำนวน "แก้หลังปิดเดือน" (นับแถว audit) พองเกินจริง
- ใช้วิธีเดียวกับทีมของหน้าเปิดงาน: **เทียบของเดิม** — ผลตรวจจับคู่ด้วย (`visit_id`, `station_id`) · งานซ่อมและทีมจับคู่ด้วย id → แก้เฉพาะที่เปลี่ยน · ลบเฉพาะที่หายไป · เพิ่มเฉพาะที่ใหม่
- **ผลต่อสถานีของงานซ่อม/ฝังเพิ่มที่บันทึกไปแล้ว:** แก้หรือลบได้เฉพาะเมื่อสถานีที่ได้รับผล **ยังไม่มีผลตรวจจากการเข้าครั้งหลัง** → ย้อนผลได้ (ลบสถานีที่ฝังใหม่ · คืนสถานะเดิม) · ถ้ามีการเข้าครั้งหลังอ้างถึงแล้ว → ปฏิเสธ `SV005` "แก้งานซ่อมนี้ไม่ได้ เพราะมีการเข้าบริการครั้งหลังใช้สถานีนี้แล้ว" (แก้ที่รอบหลังก่อน)
- ลบ visit ทั้งครั้ง = ใช้กติกาเดียวกัน + คำนวณ F ใหม่ (ข้อ 2)

## 5. RPC transaction เดียว (แบบหน้าเปิดงาน) — ทำ
`save_service_visit(p_visit jsonb)` · SECURITY INVOKER · 1 การเรียก = 1 transaction
- ข้างใน: ตรวจขอบเขต → (ครั้งแรก) สร้างสถานี IG/IC ตามจำนวน + ตั้ง `stations_initialized_at` → insert/update visit → แทนที่ทีม → แทนที่ผลตรวจ / งานซ่อม (ลบของเดิมของ visit นี้แล้วใส่ใหม่ ตอนแก้) → ผลต่อสถานะสถานี → คืน visit_id
- **หน้าจอสร้าง visit id เอง** แล้วส่งมา — กด "บันทึก + รายถัดไป" ซ้ำ (เน็ตช้า/กดสองที) ไม่เกิดการเข้า 2 ครั้ง (id ซ้ำ = แก้ครั้งเดิม)
- ทีมที่รับ: A–O และ Z เท่านั้น (ทีม `Sup` ไม่รับในหน้านี้ — ถ้าเจ้าของอยากให้เลือกได้ บอกได้)
- ใช้ **jsonb ก้อนเดียว** (ต่างจากหน้าเปิดงาน) เพราะมีรายการซ้อนหลายชุด (ทีม · พบปลวก · ไม้ · งานซ่อม · AG) — ตรวจทุกช่องใน SQL ไม่เชื่อหน้าจอ
- ตรวจเลขสถานี: ต้องมีจริงและ `active` (ยกเว้น `added`) · เลขฝังใหม่ > จำนวนเดิมของชนิด · ไม่ซ้ำในฟอร์ม
- กันลืมกล่อง (D10): ถ้ามีกล่อง AG ค้าง ทุกจุดต้องมีแถว (ตรวจแล้ว หรือ `checked = false`) หรือส่ง "ข้ามทุกจุด" → ตรวจใน RPC ด้วย
- `delete_service_visit(p_visit_id)` · error code ชุดใหม่: `SV001` เลขสถานีไม่มี/ไม่ใช้งาน · `SV002` เลขฝังใหม่ไม่ถูก · `SV003` ต้องระบุจำนวนสถานีก่อน · `SV004` กล่อง AG ยังไม่ครบ · `SV005` แก้/ลบงานซ่อมที่รอบหลังใช้ต่อแล้วไม่ได้ · `SV006` ทีมไม่ถูกต้อง/ไม่ได้เลือกทีม — ให้หน้าจอแปล

## 6. ข้อที่ต้องให้เจ้าของเลือก (4 ข้อ)

**ก. เก็บวัสดุ (เหยื่อ / เคมีผง / ไม้) แบบไหน**
- (ก1) **รายสถานี** แล้วรวมด้วย view (แนะนำ) — ย้อนดูได้ว่าใช้ที่จุดไหน · ยอดรวมตรงกับรายละเอียดเสมอ · เลิกใช้ยอดรวมเก่าใน `visits`
- (ก2) **ยอดรวมต่อการเข้า** ใน `visits` (คอลัมน์เดิม) — งานน้อยกว่า · แต่ไม่รู้ว่าเหยื่อลงจุดไหน และยอดรวมกับตารางพบปลวกอาจไม่ตรงกัน

**ข. "ไม่ได้ตรวจจุดนี้" (กล่อง AG)**
- (ข1) **เก็บเป็นแถว "ไม่ได้ตรวจ"** (แนะนำ) — มีหลักฐานว่าทีมเข้าแต่ไม่ได้ตรวจ · ระบบกันลืมกล่องได้จริง · ไม่นับเป็นรอบ F
- (ข2) ไม่เก็บอะไรเลย — ง่ายกว่า แต่แยกไม่ออกว่า "ลืมกรอก" หรือ "ตั้งใจข้าม"

**ค. ลูกค้า Renew — สถานีของสัญญาเก่าไปไหน** (สถานีผูกกับสัญญา · Renew = สัญญาใหม่)
- (ค1) **ย้ายสถานีที่ยังใช้งานไปสัญญาใหม่** (แนะนำ) — ไม่ต้องกรอกจำนวนซ้ำ · เลข F ของกล่อง AG นับต่อ · สัญญาเก่าไม่โผล่ในหน้า "รอเก็บสถานี" (เพราะของยังอยู่ใช้ต่อ) · ประวัติผลตรวจเก่ายังอยู่กับสัญญาเก่า
- (ค2) คัดลอกจำนวนไปสร้างสถานีชุดใหม่ — สัญญาเก่ายังมีสถานีค้าง ต้องปิดด้วยมือ · F ของกล่อง AG เริ่มใหม่
- (ค3) ให้หัวหน้างานกรอกจำนวนใหม่เหมือนลูกค้าใหม่ — ง่ายสุด แต่ซ้ำงาน และสัญญาเก่าจะถูกถามให้เก็บสถานีที่ยังอยู่หน้างาน

**ง. สถานะสถานีที่หาย / ถอนออก + ใช้เลขซ้ำได้ไหม** (เกี่ยวกับคำถามค้าง X2)
- (ง1) **เพิ่มสถานะใหม่ 2 ค่า "หาย" และ "ถอนออก"** แยกจาก "ถอดกล่องแล้ว (จบปัญหา)" และ "เก็บคืนแล้ว" (แนะนำ) — ตัวเลขกล่อง AG และการเก็บสถานีคืนไม่เพี้ยน · X2 ยังตัดสินแยกได้
- (ง2) ใช้สถานะเดิม (หาย/ถอน = `removed`) — ไม่เพิ่มของ แต่ปน "ถอนกลางสัญญา" กับ "จบปัญหา" ในรายงาน
- **เลขซ้ำ:** สถานีหายแล้วฝังใหม่ที่จุดเดิม จะ (ก) ใช้เลขเดิมได้ (แนะนำ — ตรงกับ site plan · ระบบบังคับเลขไม่ซ้ำเฉพาะสถานีที่ยังใช้งาน) หรือ (ข) ต้องใช้เลขใหม่เสมอ (ตาม DECISIONS 2.15 ตอนนี้: เลขใหม่ > จำนวนเดิม)

**ค่าเริ่มต้นทางเทคนิค (ทำตามนี้ ถ้าไม่มีใครค้าน):**
- หัวหน้างานเขียน `stations` ได้ผ่าน policy + trigger กันแก้ช่องสำคัญ (แก้ได้แค่สถานะ/ป้ายจุด/เพิ่มสถานีใหม่ · ลบไม่ได้)
- ย้าย `visits.team_id` เข้า `visit_teams` แล้วลบคอลัมน์
- คำนวณ F ใหม่เมื่อแก้/ลบย้อนหลัง (แก้ช่องโหว่เดิม)
- ส่งงาน 3 ก้อน: ① เวลา + หลายทีม + view เวลา · ② สถานี + ผลตรวจ + F · ③ งานซ่อม + RPC + view วัสดุ (หมวด 1 เริ่มได้ตั้งแต่ก้อน ①)

## ผลตัดสิน (เจ้าของ 12 พ.ย. 2026 — ผ่านศูนย์กลาง)
- **ก = ก1** เก็บวัสดุรายสถานี รวมด้วย view
- **ข = ข1** เก็บแถว "ไม่ได้ตรวจ" · F นับเฉพาะที่ตรวจจริง
- **ค = ค1 แบบปรับ** (คำเจ้าของ: "ย้ายไปสัญญาใหม่ แต่เป็นระบบที่แจ้งไว้ และสามารถกรอกใหม่ได้ เพราะบางครั้งต่อสัญญามีการแก้จำนวนสถานี แต่ต้องบอกประวัติของสัญญาเก่าไว้ด้วย เผื่ออ้างอิง") → ระบบ **เสนอ** สถานีที่ยังใช้ของสัญญาเก่าให้ย้าย (F นับต่อ) แต่ผู้ใช้ **แก้จำนวน/เลือกได้** ก่อนยืนยัน · **ประวัติผลบริการของสัญญาเก่าต้องเปิดดูได้เสมอ** · แบบการเก็บความเชื่อมโยงจะส่งให้ศูนย์กลางดูก่อนเขียนในก้อน ②
- **ง = ง1** แยกสถานะ "หาย" / "ถอนออก" · **ฝังแทนใช้เลขเดิมได้** (แทน DECISIONS 2.15 ส่วน "เลขใหม่ต้องมากกว่าจำนวนเดิม") แต่ต้องไม่ซ้ำกับสถานีที่ยังใช้งาน
- ค่าเริ่มต้นทางเทคนิครับทั้งหมด: สิทธิ์ recorder บน stations แบบ policy + trigger (เพิ่ม/เปลี่ยนสถานะ/ป้ายจุด · ลบไม่ได้) · ลบ `visits.team_id` · คำนวณ F ใหม่ · ส่ง 3 ก้อน
