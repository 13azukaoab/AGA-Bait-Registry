# ออกแบบ: สำรองข้อมูลอัตโนมัติ + เฝ้าดูพื้นที่ (Supabase Free)

> สถานะ: **เจ้าของเลือกแล้ว 14 พ.ย. 2026** — ที่เก็บ **Cloudflare R2** · **ศูนย์กลางสร้าง repo ส่วนตัว** · สำรอง **02:00 น.** · ยังไม่ลงมือ (ต้องตรวจเงื่อนไข/การผูกบัตรของ R2 ก่อน)
> ที่มา: DECISIONS 2.33 — ใช้จริงด้วย Supabase Free + Vercel Pro · แบบฟรีไม่มี backup อัตโนมัติ และพื้นที่จำกัด (DB 500 MB · ไฟล์ 1 GB)

## 1. สรุปสั้นสำหรับเจ้าของ

ทุกคืนระบบจะ **ก๊อปข้อมูลทั้งหมดไปเก็บอีกที่หนึ่งแบบล็อกรหัส** (ข้อมูลลูกค้า + ไฟล์ PDF ที่เพิ่มใหม่) เก็บย้อนหลังได้หลายเดือน
ถ้าวันไหนข้อมูลพัง ถูกลบผิด หรือ Supabase มีปัญหา → **เอาข้อมูลคืนได้** (เสียข้อมูลไม่เกิน 1 วัน)
และทุกวันจันทร์ รายงานตรวจสุขภาพที่เด้งเข้ามือถือ จะบอก **% พื้นที่ที่ใช้ไป** + เตือนเมื่อเกิน 70% จะได้ตัดสินใจอัปเกรดทัน

ค่าใช้จ่าย: **0 บาท** (ใช้บริการฟรีทั้งหมด) · สิ่งที่เจ้าของต้องทำเอง: สร้างบัญชีที่เก็บ + ตั้งรหัสลับ 3–4 ตัว (ผมบอกทีละขั้น ไม่ต้องส่งรหัสให้ผม)

## 2. ภาพรวมการทำงาน

```
ทุกคืน 02:00 (เวลาไทย)
  GitHub Actions (repo ส่วนตัวแยก "AGA-Bait-Registry-backup")
    ① ดึงข้อมูลจาก Supabase  — ด้วยบัญชี "อ่านอย่างเดียว"
         • ฐานข้อมูลทั้งหมด (โครงสร้าง + ข้อมูล)        → ไม่กี่ MB หลังบีบอัด
         • ไฟล์ใน bucket `contract-files` ที่เพิ่มใหม่   → เฉพาะไฟล์ใหม่ (ไม่ก๊อปซ้ำ)
    ② บีบอัด + ล็อกรหัส (เข้ารหัสด้วยรหัสผ่านที่เจ้าของเก็บเอง)
    ③ ส่งไปเก็บที่ปลายทาง (ตัวเลือก ก/ข/ค ข้อ 4)
    ④ ลบไฟล์สำรองเก่าตามรอบ (เก็บรายวัน 14 · รายสัปดาห์ 8 · รายเดือน 12)
    ⑤ วัดพื้นที่ DB / ไฟล์ → ถ้าเกิน 70% ให้งานขึ้น "ล้มเหลว" → GitHub ส่งอีเมลเตือนเจ้าของทันที

ทุกวันจันทร์ 08:30 (Routine บน cloud ที่มีอยู่แล้ว)
    + เพิ่มหัวข้อ "พื้นที่ใช้ไป DB __% · ไฟล์ __%" และ "สำรองข้อมูลล่าสุดสำเร็จเมื่อ ___"
```

ผลพลอยได้: งานกลางคืนแตะฐานข้อมูลทุกวัน → ช่วยกันโปรเจกต์ถูกหยุดเพราะ "ใช้น้อย 7 วัน" (Supabase ไม่ได้นิยามชัดว่านับอะไร จึงถือเป็นผลพลอยได้ ไม่ใช่การรับประกัน)

## 4. ที่เก็บไฟล์สำรอง — ให้เจ้าของเลือก

| | ก. Cloudflare R2 ⭐ แนะนำ | ข. Google Drive (บัญชีบริษัท) | ค. Backblaze B2 |
|---|---|---|---|
| ฟรี | ~10 GB | 15 GB/บัญชี (Workspace = พื้นที่รวม) | ~10 GB |
| พอไหม | DB สำรองรวมทุกรอบ < 1 GB + PDF ≤ 1 GB → **พอสบาย** | พอ | พอ |
| ใช้ PDF ต่อในอนาคต | ✅ ถ้าพื้นที่ไฟล์ Supabase เต็ม ย้าย PDF มาที่ R2 ได้เลย (ที่เดียวกัน) | ❌ ใช้เป็นที่เก็บไฟล์ของแอปไม่สะดวก | ✅ ได้ |
| ตั้งค่า | สร้างบัญชี Cloudflare + bucket + key (อาจต้องผูกบัตร ยังไม่ยืนยัน) | สร้าง service account + แชร์โฟลเดอร์ (ขั้นตอนเยอะกว่า) | สร้างบัญชี + bucket + key |
| ข้อควรตรวจก่อนใช้ | เงื่อนไขเชิงธุรกิจ + ต้องผูกบัตรไหม (ยังไม่ยืนยัน) | — | เงื่อนไขแผนฟรีล่าสุด |

**แนะนำ ก** เพราะถ้า PDF เต็ม 1 GB ใน Supabase จะย้าย PDF มาที่ R2 ที่เดียวกันได้เลย (ตรงกับที่เจ้าของบอก "ถ้าเต็มค่อยปรับส่วนนั้น") · ก่อนตั้งค่าจริง ศูนย์กลางตรวจหน้าราคา/เงื่อนไขล่าสุดก่อน

## 5. ความปลอดภัย (ข้อมูลลูกค้า · PDPA)

1. **บัญชีอ่านอย่างเดียว:** สร้าง role ใหม่ในฐานข้อมูลชื่อ `backup_reader` อ่านได้อย่างเดียว เขียน/ลบไม่ได้ · ใช้ role นี้ดึงข้อมูล ไม่ใช้รหัส `postgres` ตัวหลัก → ถ้ารหัสสำรองหลุด คนอื่นก็แก้ข้อมูลไม่ได้
   - role สร้างด้วย migration (ไม่มีรหัสในไฟล์) · **เจ้าของตั้งรหัสเองใน Supabase SQL Editor** (ศูนย์กลางเตรียมคำสั่งให้ เว้นช่องรหัส)
   - ไฟล์ PDF ดึงด้วย key ที่อ่านได้อย่างเดียวเฉพาะ bucket (ถ้า Supabase ทำได้) ถ้าไม่ได้ ใช้ service key เก็บใน secret ของ repo ส่วนตัว
2. **ล็อกรหัสก่อนส่งออก:** ไฟล์สำรองเข้ารหัสด้วย `age` (หรือ `gpg --symmetric`) ก่อนออกจากเครื่องรัน · ที่ปลายทางเห็นแค่ไฟล์ที่อ่านไม่ออก
   - **รหัสผ่านถอดรหัส เจ้าของเก็บเอง** (เช่น ตัวจัดการรหัสผ่าน + จดเก็บในที่ปลอดภัย) — ⚠ **ถ้ารหัสนี้หาย ไฟล์สำรองทั้งหมดใช้ไม่ได้**
3. **รหัสลับทั้งหมดอยู่ใน GitHub Secrets ของ repo ส่วนตัว** · ห้ามพิมพ์ลง log · ห้ามส่งในแชท · ศูนย์กลางไม่เห็นค่า
4. log ของงานพิมพ์แค่ "สำเร็จ / ขนาดไฟล์ / % พื้นที่" ไม่พิมพ์ข้อมูลลูกค้า
5. จำกัดคนเข้าถึง repo ส่วนตัว + ที่เก็บ = เจ้าของ (และคนที่เจ้าของอนุญาต)
6. ลบไฟล์สำรองเก่าอัตโนมัติตามรอบ (ไม่เก็บข้อมูลลูกค้าเกินจำเป็น)

## 6. การกู้คืน (ต้องซ้อมจริง)

- คู่มือทีละขั้นภาษาไทย `docs/คู่มือกู้คืนข้อมูล.md`: ดาวน์โหลดไฟล์ → ถอดรหัส → กู้เข้า **ฐานข้อมูลทดสอบในเครื่องก่อน** → ตรวจตัวเลข → ค่อยกู้ขึ้น cloud (เฉพาะเจ้าของสั่ง)
- **ซ้อมกู้คืนเดือนละครั้ง** บนฐานข้อมูลในเครื่อง (ศูนย์กลางทำ · ไม่แตะ cloud) — สำรองที่ไม่เคยซ้อมกู้ = เชื่อไม่ได้
- เป้าหมาย: เสียข้อมูลไม่เกิน 1 วัน · กู้เสร็จภายในครึ่งวัน

## 7. เฝ้าดูพื้นที่

| วัด | วิธี | เตือนเมื่อ |
|---|---|---|
| ขนาดฐานข้อมูล | `pg_database_size(current_database())` เทียบ 500 MB | ≥ 70% (350 MB) |
| ขนาดไฟล์ | รวม `metadata->>'size'` ใน `storage.objects` ของ `contract-files` เทียบ 1 GB | ≥ 70% (700 MB) |
| สำรองล่าสุด | เวลาไฟล์ล่าสุดที่ปลายทาง | เกิน 36 ชม. ไม่มีไฟล์ใหม่ |

แจ้ง 2 ทาง: งานกลางคืน (อีเมลจาก GitHub ทันทีเมื่อเกิน) + รายงานวันจันทร์ (มือถือ)
