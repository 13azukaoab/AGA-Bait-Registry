## รายละเอียดแต่ละข้อ

### SEC-01 · สมัครสมาชิกเองได้บน cloud? (กลาง · มีเงื่อนไข · **ยังไม่ได้ตรวจบน cloud**)
- **สิ่งที่ตรวจแล้ว (จากโค้ด):** `supabase/config.toml:177` `enable_signup = true` และ `:228` `enable_confirmations = false` (ไฟล์นี้ใช้กับฐานข้อมูลในเครื่อง — บน cloud จะเหมือนกันหรือไม่ขึ้นกับว่าเคยตั้งค่าใน Dashboard ไว้อย่างไร) · ใน `docs/` ไม่พบบันทึกว่าเคยปิดการสมัครบน cloud
- **ผลถ้าเปิดอยู่:** คนนอกเรียก `/auth/v1/signup` ด้วย anon key (ซึ่งอยู่ในเบราว์เซอร์ทุกเครื่องอยู่แล้ว) → ได้ JWT role `authenticated` ที่ **ไม่มีแถว profiles**
  - อ่านได้: ตารางที่ policy เป็น `TO authenticated USING (true)` — `zones`, `branches`, `teams`, `customer_types`, `tier_rules` (`20261104100318_rls_policies.sql:144-160`), `positions` (`20261110090300_positions_and_profile_accounts.sql:46`), `app_settings` (`20261115170000_app_settings_workload.sql:101`) และ view `v_paused_branch_summary` (GRANT ให้ authenticated · `20261115300001_contract_pause.sql:780`) · เรียก `contract_month_paused` ได้ (SEC-05)
  - **อ่านไม่ได้:** ข้อมูลลูกค้าทุกตาราง เพราะ `current_app_role()` คืน NULL เมื่อไม่มีโปรไฟล์ (`20261110090300_positions_and_profile_accounts.sql:146`) และฟังก์ชัน RPC ที่สุ่มตรวจปฏิเสธ role NULL ทั้งหมด · middleware ก็ตัด session ทิ้งเมื่อไม่มีโปรไฟล์ (`middleware.ts:62-69`)
- **วิธีตรวจแบบไม่สร้างบัญชี (ให้ HQ/เจ้าของทำ):** Supabase Dashboard → Authentication → Sign In / Providers → ดูสวิตช์ "Allow new users to sign up" หรือเปิด `https://<project>.supabase.co/auth/v1/settings?apikey=<anon key>` แล้วดูค่า `disable_signup` · **ห้ามทดสอบด้วยการสมัครจริง** (จะเกิดบัญชีขยะบน production)
- **ทางแก้:** ปิดการสมัคร — ไม่กระทบระบบเพราะบัญชีพนักงานสร้างผ่าน `auth.admin.createUser` (`lib/admin/userAdmin.ts:241`) ซึ่งไม่ขึ้นกับสวิตช์นี้ · แก้ `config.toml:177` เป็น `false` ให้ในเครื่องตรงกับ cloud

### SEC-02 · ไม่มี security header (กลาง)
- **หลักฐาน:** curl `/` และ `/login` บน production ไม่มี CSP, X-Frame-Options / frame-ancestors, X-Content-Type-Options, Referrer-Policy, Permissions-Policy · `next.config.ts:7-16` ไม่มี `headers()` และ `vercel.json` ไม่มี `headers` · มี HSTS แล้ว (Vercel ใส่ให้)
- **ทำไมสำคัญกับระบบนี้:** คุกกี้ session ของ `@supabase/ssr` ไม่ใช่ HttpOnly (ฝั่ง browser client ต้องอ่าน) → ถ้าเกิด XSS ที่ใดก็ตาม = ขโมย session ได้ · CSP คือด่านสำรองที่ลดความเสียหาย · ไม่มี frame-ancestors = หน้าปิดเดือน/จัดการผู้ใช้ของ host ถูกฝังในเว็บอื่นเพื่อหลอกกดได้
- **ข้อควรระวังตอนแก้:** มี inline script หลายจุด — `components/shell/ThemeScript.tsx:8`, `components/shell/AppShell.tsx:167`, Clarity (`components/analytics/Clarity.tsx:20`), Sentry และ Serwist · ต้องอนุญาตโดเมน Supabase (connect/img), `clarity.ms`, Sentry ingest · จึงแนะนำทำ 2 ขั้น: (1) ใส่ header ที่ไม่เสี่ยงพังทันที (frame-ancestors/XFO, nosniff, Referrer-Policy, Permissions-Policy, `poweredByHeader: false`) (2) CSP แบบ `Content-Security-Policy-Report-Only` สัก 1–2 สัปดาห์ก่อนบังคับจริง

### SEC-03 · dependency (ต่ำ)
- **วิธีตรวจ:** `npm audit --omit=dev` กับ `package-lock.json` (ในเครื่องไม่มี `node_modules` — ไม่ได้ติดตั้งเพิ่มตามข้อห้าม) → moderate 1 (`next`), high 1 (`postcss` ที่ซ้อนใน `next/node_modules/postcss@8.4.31`) · critical 0
- **เข้าเงื่อนไขจริงไหม:**
  - postcss (high): ช่องโหว่เกิดตอนประมวลผล CSS ที่ผู้โจมตีควบคุม — ระบบนี้ใช้ตอน build กับ CSS ของเราเอง → ใช้โจมตีตอนรันไม่ได้
  - GHSA-f3mh-rxg3-f5g2 (คุกกี้ HttpOnly รั่วผ่าน header `x-middleware-set-cookie`): เงื่อนไขคือ **route handler แบบ Edge runtime ที่ตั้งคุกกี้ผ่าน NextResponse** — grep แล้วไม่มี route ไหนตั้ง `runtime = "edge"` (middleware เป็น Edge แต่ advisory ไม่ได้ระบุ middleware) และคุกกี้ Supabase ไม่ใช่ HttpOnly อยู่แล้ว → ผลกระทบต่ำ
  - SVG ใน image optimization: ไม่ได้ใช้ `next/image` (grep ไม่พบ) → ไม่เข้าเงื่อนไข
  - Cross-client response injection: เฉพาะ self-hosted ที่ส่งต่อ response → ระบบนี้อยู่บน Vercel
- **ทางแก้:** อัปเป็น `next@15.5.29` (เวอร์ชันแก้ของสาย 15) เป็นงานบำรุงรักษาปกติ

### SEC-04 · เปลี่ยนรหัสโดยไม่ถามรหัสเดิม (ต่ำ)
- `changePasswordAction` เรียก `supabase.auth.updateUser({ password })` ทันทีหลังตรวจว่าล็อกอิน (`app/(auth)/change-password/actions.ts:41-49`) · local `secure_password_change = false` (`supabase/config.toml:230`)

### SEC-05 · `contract_month_paused` เป็น denylist (ต่ำ)
- `AND current_app_role() IS DISTINCT FROM 'viewer'` (`20261115300001_contract_pause.sql:130`) — ค่า NULL (ไม่มีโปรไฟล์ / `is_active = false`) ผ่านเงื่อนไขนี้
- ฟังก์ชันอื่นที่ตรวจใช้แบบ allowlist ทั้งหมด (เช่น `get_sync_status`, `list_month_closures`, `customer_contact_is_cross_team`) — ข้อนี้จึงเป็นจุดเดียวที่ไม่สม่ำเสมอ
- ต้องรู้ UUID สัญญาก่อนจึงจะถามได้ และคืนแค่ true/false → ต่ำ · ถ้าแก้ต้องระวัง trigger ที่เรียกฟังก์ชันนี้ในบริบท service_role / import

## BUG-3 — บัญชีที่ถูกปิดล็อกอินแล้วขึ้น "รหัสผ่านไม่ถูกต้อง"

### สาเหตุ (root cause)
1. ตอนปิดบัญชี ระบบทำ 2 ชั้น: ตั้ง `profiles.is_active = false` แล้ว **แบนที่ Supabase Auth (GoTrue)** ด้วย `ban_duration: "876000h"` (`lib/admin/userAdmin.ts:316-318`, เรียกจาก `components/admin/userActions.ts:112-122`)
2. ตอนล็อกอิน บัญชีที่ถูกแบนจะถูก GoTrue ปฏิเสธตั้งแต่ `signInWithPassword` → โค้ดแปลง error ทุกชนิดเป็นข้อความเดียว `GENERIC_ERROR` (`app/(auth)/login/actions.ts:56-58`)
3. ข้อความ "บัญชีนี้ถูกปิดการใช้งาน" (`DISABLED_ERROR`, `login/actions.ts:70-72`) จึง **ไม่มีทางถูกแสดง** กับบัญชีที่ถูกแบน — ทำงานเฉพาะกรณี `is_active = false` แต่ไม่ได้แบน (เช่น แบนไม่สำเร็จ)

### GoTrue ตรวจ "ถูกแบน" ก่อนหรือหลังตรวจรหัส? (สำคัญต่อการเลือกทาง)
- **ตรวจแล้ว (จาก source code):** ไฟล์ `internal/api/token.go` ของ `supabase/auth` สาขา master (ดึงอ่าน 27 พ.ย. 2026) ฟังก์ชัน password grant: หาผู้ใช้ → **ตรวจ `user.IsBanned()` แล้วคืน error `user_banned` ("User is banned")** → **แล้วจึงตรวจรหัสผ่าน** · รหัสผิด/ไม่มีผู้ใช้ คืน `invalid_credentials` ข้อความเดียวกัน
- แปลว่า: **ถ้ากรอก username ของบัญชีที่ถูกปิด + รหัสอะไรก็ได้ (แม้ผิด) Supabase จะตอบว่า "ถูกแบน"**
- **ยังไม่ได้ตรวจ:** เวอร์ชัน GoTrue ที่รันบน cloud จริง (ไม่ได้ทดลองล็อกอินบน production) — สมมติว่าพฤติกรรมเหมือน master

### ทางเลือก

| ทาง | ทำอะไร | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **ก** คงข้อความเดียว | ไม่แก้ (หรือแก้แค่คอมเมนต์ให้รู้ว่า DISABLED_ERROR ไม่ทำงานกับบัญชีที่แบน) | ไม่รั่วอะไรเลย · ไม่ต้องแก้โค้ด | ผู้ใช้ที่ถูกปิดสับสน คิดว่าลืมรหัส แล้วไปขอ host รีเซ็ต (ซึ่งไม่ช่วย) |
| **ข** แสดง "บัญชีถูกปิด" เมื่อ Supabase ตอบ `user_banned` | ตรวจ `error.code === "user_banned"` ใน `login/actions.ts:56` แล้วคืน `DISABLED_ERROR` | ผู้ใช้รู้ทันทีว่าต้องติดต่อ host | **ไม่ได้เป็น "หลังรหัสถูกเท่านั้น" อย่างที่คาดไว้** — จากข้อเท็จจริงข้างบน ใครรู้แค่ username ก็รู้ได้ว่าบัญชีนั้น "มีอยู่และถูกปิด" (user enumeration เฉพาะบัญชีที่ปิดแล้ว) · ผลเสียจริงน้อย เพราะบัญชีที่ปิดเอาไปใช้ทำอะไรไม่ได้ แต่ขัดกับหลักที่เขียนไว้ในหัวไฟล์ login (`login/actions.ts:9-10`) · ถ้าจะให้ขึ้น "หลังรหัสถูกเท่านั้น" จริง ต้อง **เลิกแบนที่ GoTrue** แล้วพึ่ง `is_active` อย่างเดียว = ตัดชั้นป้องกันออก 1 ชั้น (ไม่แนะนำ) |
| **ค** ข้อความกลาง + คำแนะนำ | เปลี่ยน `GENERIC_ERROR` เป็น "ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง — ถ้าลืมรหัสหรือบัญชีถูกปิด ติดต่อ Host (QCS ส่วนกลาง Bait)" | ไม่รั่ว · ผู้ใช้รู้ว่าต้องไปหาใคร · แก้ 1 บรรทัด | ผู้ใช้ยังไม่รู้แน่ว่าเป็นกรณีไหน (host ดูสถานะบัญชีในหน้าจัดการผู้ใช้แล้วบอกได้ทันที) |

### คำแนะนำ: **ค** (แก้ข้อความใน `app/(auth)/login/actions.ts:27` · งาน FE+BE เล็ก)
ปลอดภัยที่สุดและแก้ปัญหาที่ผู้ใช้เจอจริง (ไม่รู้ว่าต้องติดต่อใคร) · ถ้าเจ้าของอยากให้ผู้ใช้รู้ชัดว่าถูกปิด **ข** ก็รับได้ เพราะสิ่งที่รั่วคือ "บัญชีนี้ถูกปิดแล้ว" ซึ่งมีมูลค่าต่อผู้โจมตีต่ำ — แต่ต้องรู้ว่ามันรั่วโดยไม่ต้องรู้รหัส

## ข้อจำกัดการตรวจ (สิ่งที่ยังไม่ได้ยืนยัน)

1. **ไม่ได้ทดสอบ RLS กับ cloud จริง** — ไม่ได้ล็อกอินเป็นแต่ละตำแหน่งแล้วลองอ่านข้อมูล · ข้อสรุปเรื่องสิทธิ์มาจากการอ่าน migration (นิยามล่าสุดชนะ) + ผล advisor เท่านั้น · ถ้า cloud มีการแก้ด้วยมือนอก migration จะไม่เห็น
2. **ไม่ได้รัน pgTAP / ฐานข้อมูลในเครื่อง** (ข้อห้ามของงานนี้)
3. **ค่าตั้ง Auth บน cloud** (สมัครเอง / ยืนยันอีเมล / secure password change / rate limit) — ดูได้แค่ `config.toml` ของเครื่อง → SEC-01, SEC-04 มีเงื่อนไข
