# แผนนำเข้าข้อมูลขึ้น cloud — จันทร์ 23 พ.ย. 2026

> งานหมวด 4 (DATA) · เขียน 19 พ.ย. 2026 · **เอกสารสำหรับขออนุมัติเท่านั้น — ยังไม่มีใครแตะ cloud**
> นำเข้า 2 ชุด: ตัวเลข Dashboard เดิม (legacy 903 แถว) + ทะเบียน OCT.26 ทั้ง 24 สาขาส่วนกลาง (2,369 สัญญา + 2,278 เบอร์)
> ผลทดลองบน DB ในเครื่อง (ผ่านครบทุกข้อ): `docs/legacy-snapshots-import.md` · `docs/ผลนำเข้าทะเบียน-24สาขา-OCT26-DBในเครื่อง.md`
> เอกสารนี้ไม่มีชื่อ/เบอร์/ที่อยู่ลูกค้า และไม่มี URL/key จริงของ cloud — ค่าที่เจ้าของตั้งเขียนเป็น `<ค่าที่เจ้าของตั้ง>`

## สรุปสั้น (สำหรับเจ้าของ)
- **ยังรันขึ้น cloud ไม่ได้ทันที** — สคริปต์ทั้ง 2 ตัวตอนนี้ปฏิเสธ URL ที่ไม่ใช่ localhost (ตั้งใจไว้) · ต้องแก้โค้ดตามหัวข้อ 3 ก่อน แล้วให้ตรวจ/merge ตามขั้นตอนปกติ
- ลำดับ: **สำรองข้อมูล → ตรวจ cloud (อ่านอย่างเดียว) → legacy → ทะเบียน → ตรวจยอด** · ทุกขั้น dry-run ก่อนเขียนจริง · ตัวเลขไม่ตรง = หยุด
- คนกดรัน: **เจ้าของ (หรือผู้ดูแลฐานข้อมูลที่เจ้าของมอบหมาย) บนเครื่องที่มีไฟล์ fixtures** · service_role key ตั้งใน env ของเครื่องนั้นเองตอนรัน · Claude/session ไม่เห็น key
- เวลาโดยประมาณ **1.5–2 ชั่วโมง** (รวมสำรองและตรวจ) · ควรทำช่วงที่ไม่มีผู้ใช้ และ**ไม่คร่อมเวลา Auto Sync 06:00 น.** (หัวข้อ 6)

## 1. ก่อนเริ่ม (อ่านอย่างเดียว · ทำได้ตั้งแต่ก่อนวันจริง)

### 1.1 สำรองข้อมูล (บังคับ · ทำก่อนแตะอะไร)
Supabase แพ็กเกจฟรีไม่มี backup รายวันให้ (DECISIONS 2.33 / X1) — ที่มีคือ **งานสำรองของเราเอง** (GitHub Actions ใน repo ส่วนตัว `AGA-Bait-Registry-backup` · ไฟล์เข้ารหัสด้วย age เก็บใน Cloudflare R2 · ดู `docs/คู่มือกู้คืนข้อมูล.md`)

| ขั้น | ใครทำ | ผ่านเมื่อ |
|---|---|---|
| กดรันงานสำรองเอง (workflow `backup.yml` มีปุ่มรันเอง) **ในวันนั้นก่อนเริ่ม** | เจ้าของ (มีสิทธิ์ repo ส่วนตัว) | งานขึ้นสีเขียว · มีไฟล์ `daily/db-2026-11-23.tar.age` ใน R2 · รายงานจำนวนแถวต่อตาราง |
| จดจำนวนแถวที่งานสำรองรายงาน (ไว้เทียบตอนกู้) | เจ้าของ | มีตัวเลขเก็บไว้ |
| ยืนยันว่ามี private key ของ age (`aga-backup-key.txt`) อยู่ในตัวจัดการรหัสผ่าน | เจ้าของ | เปิดเจอ — **ไม่มี key = กู้ไม่ได้ = ห้ามเริ่ม** |
| (แนะนำ) ซ้อมกู้ไฟล์นั้นลง DB ในเครื่องตามคู่มือกู้คืน ขั้น 1–3 | HQ (ไม่แตะ cloud) | ขึ้น "ตรง: … ตาราง" |

⚠ ไม่รู้: งานสำรองคืนล่าสุดสำเร็จหรือไม่ / ซ้อมกู้รอบล่าสุดเมื่อไหร่ — **HQ ต้องตรวจก่อน 23 พ.ย.** ถ้างานสำรองล้มหรือยังไม่เคยซ้อมกู้ผ่าน ให้เลื่อนการนำเข้า

### 1.2 ตรวจสภาพ cloud (SQL อ่านอย่างเดียว)
รันใน SQL Editor ของ Supabase (ผู้ดูแลฐานข้อมูล) — ขึ้นต้นด้วย `BEGIN READ ONLY;` และจบด้วย `ROLLBACK;` ทุกครั้ง

| ตรวจ | ค่าที่ต้องได้ | ไม่ตรง = |
|---|---|---|
| migration บน cloud ครบถึง main (ล่าสุดตอนเขียน = `20261115290000_contract_import_batch` · M41) — `SELECT version FROM supabase_migrations.schema_migrations ORDER BY version DESC LIMIT 5;` | มี 20261115290000 (หรือใหม่กว่าที่อยู่ใน main วันนั้น) | หยุด ให้ HQ ส่ง migration ขึ้นก่อน (กฎ "migration ถึงก่อนโค้ด") |
| คอลัมน์ `contracts.import_batch` มีจริง — `SELECT count(*) FROM information_schema.columns WHERE table_name='contracts' AND column_name='import_batch';` | 1 | หยุด |
| `SELECT public.go_live_month();` | 2026-10-01 | หยุด ถามเจ้าของ (DECISIONS 2.75) |
| `SELECT tier, min_annual, effective_month FROM tier_rules ORDER BY effective_month, min_annual;` | ชุดเดียว 2000-01-01: S 0 · M 30,000 · L 50,000 · XL 100,000 | **หยุด** — ยอดคาดในเอกสารนี้คิดจากเกณฑ์ชุดนี้ (มีชุดอื่น = ยอดเปลี่ยน ต้องคำนวณใหม่ก่อน) |
| `branches` มีครบ 43 และชื่อ 24 สาขาส่วนกลางตรง (ตัวนำเข้าตรวจซ้ำเองและหยุดถ้าขาด) — `SELECT count(*) FROM branches;` | 43 | หยุด |
| `teams` ทีมกลาง A–O (service) + Z (install) เปิดใช้ — `SELECT code, kind, is_active FROM teams WHERE branch_id IS NULL ORDER BY code;` | A–O, Z active · Sup = supervisor | ตัวนำเข้าหยุดเองถ้าทีมใช้ไม่ได้ |
| `customer_types` ป้ายตรง master 14 ค่า และเปิดใช้ (ตัวนำเข้าใช้ 10 ป้าย · หยุดเองถ้าขาด/ปิด) — `SELECT code, label, is_active FROM customer_types ORDER BY sort_order;` | 14 แถว active | ถามเจ้าของ |
| **ไม่มีลูกค้า/สัญญาใน 24 สาขาส่วนกลาง** — `SELECT count(*) FROM customers cu JOIN branches b ON b.id=cu.branch_id WHERE b.division='central';` และ `SELECT count(*) FROM contracts;` | 0 และ 0 | **หยุด** — ตัวนำเข้าปฏิเสธอยู่แล้ว (มีข้อมูล = ไม่เขียน) · ถ้าเป็นข้อมูลทดสอบ/UAT ต้องให้เจ้าของตัดสินว่าจะล้างไหม (ห้ามล้างเอง) |
| **ไม่มี snapshot เดือน 2025-01…2026-09** — `SELECT source, count(*) FROM monthly_branch_snapshots WHERE month_key BETWEEN '2025-01' AND '2026-09' GROUP BY 1;` | ไม่มีแถว | มี legacy ครบ 903 อยู่แล้ว = ข้ามขั้น legacy · มี source อื่น = หยุด (ตัวนำเข้า legacy ปฏิเสธเอง) |
| ไม่มีเดือนที่ปิดแล้วซ้อน — `SELECT * FROM month_closures ORDER BY month_key;` | ไม่มีแถวเดือน 2026-10 ขึ้นไป | ถาม HQ (ปิด OCT.26 แล้ว = ยอด OCT จะถูกตรึงจาก snapshot ไม่ใช่ทะเบียน) |

## 3. สิ่งที่ต้องแก้โค้ดก่อนรันจริง (ข้อเสนอ · ยังไม่ได้แก้)
ตอนนี้ทั้ง `scripts/import-central-registry.ts` และ `scripts/import-legacy-snapshots.ts` **ปฏิเสธทุก URL ที่ไม่ใช่ localhost** — ตั้งใจไว้ ห้ามลบด่านนี้เฉยๆ · เสนอให้เพิ่มทางเข้า cloud แบบต้องยืนยันหลายชั้น:

1. **flag `--target cloud`** — ไม่ใส่ = ทำงานแบบเดิม (localhost เท่านั้น) · ใส่ = ยอมเฉพาะ host รูป `<ref>.supabase.co` (https) เท่านั้น
2. **ต้องพิมพ์ project ref ซ้ำ**: `--project-ref <ref>` ต้องตรงกับ subdomain ใน `NEXT_PUBLIC_SUPABASE_URL` และตรงกับ env `AGA_CLOUD_PROJECT_REF` ที่เจ้าของตั้ง (3 ที่ต้องตรงกัน) — กันชี้ผิดโปรเจกต์
3. **ยืนยันก่อนเขียน**: `--apply` บน cloud ต้องพิมพ์ยืนยันในเทอร์มินัล หลังสคริปต์แสดงตัวเลขที่จะเขียน เช่น พิมพ์ `นำเข้า 2369` (ทะเบียน) / `นำเข้า 903` (legacy) · ไม่ตรง = ยกเลิก · ไม่มี flag ข้ามการยืนยัน
4. **dry-run บังคับก่อน**: `--apply` บน cloud ต้องมีไฟล์ผล dry-run ของ ref เดียวกันที่รันไม่เกิน 30 นาที (หรือให้สคริปต์ทำ dry-run ในตัวแล้วแสดงก่อนถามยืนยัน) — แบบหลังง่ายกว่า
5. **บันทึกผลเป็นไฟล์** (ตัวเลขรวม/เลขแถวเท่านั้น · ไม่มี key/URL) เก็บไว้เป็นหลักฐาน เช่น `import-log-<วันที่>.json` นอก repo
6. **สคริปต์ถอยกลับ** `scripts/rollback-registry-import.ts --batch registry-OCT26` (service_role · dry-run ก่อน · หยุดถ้ามี visits ผูกสัญญาที่จะลบ) — แทนการให้คนพิมพ์ SQL ลบเองตอนตกใจ (หัวข้อ 5)
7. ไม่เปลี่ยน: service_role ผ่าน PostgREST เท่านั้น (ห้าม role postgres — CLAUDE.md) · ไม่ import `lib/supabase/admin.ts` · เกณฑ์ Tier อ่านจาก DB · ไม่พิมพ์ชื่อ/เบอร์
8. เทส: ทาง localhost เดิมต้องเหมือนเดิม · `--target cloud` ปฏิเสธ host ที่ไม่ใช่ `*.supabase.co` / ref ไม่ตรง / ไม่พิมพ์ยืนยัน (เทสด้วย client ปลอม ไม่ต่อ cloud จริง)

**key:** เจ้าของตั้ง `NEXT_PUBLIC_SUPABASE_URL=<ค่าที่เจ้าของตั้ง>` และ `SUPABASE_SERVICE_ROLE_KEY=<ค่าที่เจ้าของตั้ง>` ใน env ของเทอร์มินัลบนเครื่องที่รันเท่านั้น (ไม่เขียนลงไฟล์ใน repo · ไม่ commit · **ไม่วางในแชท**) · ปิดเทอร์มินัลหลังเสร็จ · ถ้าสงสัยว่า key หลุด → หมุน key ใน Supabase แล้วอัปเดต env ของ Vercel

**ใครกดรัน:** เจ้าของ (หรือผู้ดูแลฐานข้อมูลที่เจ้าของมอบหมายเป็นข้อความ) · HQ/หมวด 4 อยู่ในสายเพื่ออ่านผลตัวเลข (ไม่เห็น key)

## 4. ตรวจหลังนำเข้า (อ่านอย่างเดียว)
รันใน SQL Editor ห่อด้วย `BEGIN READ ONLY; … ROLLBACK;` · คู่กับ `--verify-only` ของสคริปต์ (คำนวณยอด OCT.26 ด้วย `lib/rules` ทางเดียวกับ Auto Sync — เป็นตัวตัดสินหลัก · SQL เป็นตัวตรวจซ้ำ)

### 4.1 legacy
```sql
SELECT count(*) AS rows, sum(cust) AS cust, sum(value) AS value,
       count(DISTINCT month_key) AS months, count(DISTINCT branch_id) AS branches
  FROM monthly_branch_snapshots
 WHERE source = 'legacy' AND month_key BETWEEN '2025-01' AND '2026-09';
-- ต้องได้ 903 · 61,110 · 3,165,298,529.76 · 21 เดือน · 43 สาขา
```

### 4.2 ทะเบียน
```sql
-- จำนวนรวม
SELECT count(*) FILTER (WHERE import_batch = 'registry-OCT26') AS imported,   -- 2,369
       count(*) FILTER (WHERE import_batch IS NULL)              AS app_made,   -- 0 (ถ้ายังไม่มีคนเปิดงานในแอป)
       count(*) FILTER (WHERE status = 'expired_pending_collection') AS expired -- 1 (พระราม 2 · CT23-0003656)
  FROM contracts;

SELECT count(*) FROM customers cu JOIN branches b ON b.id = cu.branch_id WHERE b.division = 'central';  -- 2,369
SELECT count(*) AS phones, count(DISTINCT customer_id) AS customers FROM customer_phones;            -- 2,278 · 2,273
SELECT count(*) FROM contract_teams ct JOIN contracts c ON c.id = ct.contract_id
 WHERE c.import_batch = 'registry-OCT26';                                                            -- 2,369

-- M28b: Renew ไม่ผูกสัญญาเก่าที่ "จะขึ้นรายการ" (เงื่อนไขเดียวกับ list_unlinked_renewals) ต้องไม่มีสัญญานำเข้า
SELECT count(*) FROM contracts c
 WHERE c.sale_type = 'renew' AND c.renewed_from_contract_id IS NULL
   AND c.unlinked_closed_at IS NULL AND c.import_batch IS NULL;                                       -- 0
SELECT pg_get_functiondef('public.list_unlinked_renewals(uuid)'::regprocedure) LIKE '%c.import_batch IS NULL%';  -- true

-- ยอด OCT.26 ต่อสาขา: สัญญาที่เดือนบริการครอบ ต.ค. 2026 (เดือนเริ่ม … เดือนเริ่ม + term_months − 1) และไม่ถูกยกเลิก
-- (ไม่มี visits ตอนนำเข้า → ไม่มีเดือนชดเชย · ตัวเลขต้องเท่ากับตารางหัวข้อ 2 ของรายงานผลนำเข้า)
SELECT b.name, count(*) AS cust, sum(c.value_total) AS value
  FROM contracts c JOIN customers cu ON cu.id = c.customer_id JOIN branches b ON b.id = cu.branch_id
 WHERE c.import_batch = 'registry-OCT26'
   AND c.status <> 'cancelled'
   AND date_trunc('month', c.start_date) <= DATE '2026-10-01'
   AND date_trunc('month', c.start_date) + make_interval(months => c.term_months - 1) >= DATE '2026-10-01'
 GROUP BY b.name ORDER BY b.name;
-- รวมต้องได้ 2,366 / 132,947,645.82 · รายสาขาเทียบตาราง "ยอด OCT.26 ต่อสาขา" (เช่น พุทธมณฑล 230 / 14,496,636.86 · นครปฐม 31 / 1,972,860.07)
```
⚠ SQL ชุดนี้ **ยังไม่ได้ลองรันจริง** (เขียนจากโครงสร้างตาราง) — ต้องลองบน DB ในเครื่องหลังนำเข้าในรอบซ้อม (หัวข้อ 1.3) ให้ได้ตัวเลขตรงก่อนใช้กับ cloud · การแยก Tier 8 แบบให้ดูจาก `--verify-only` (สูตรอยู่ใน `lib/rules` ไม่เขียนซ้ำใน SQL)

## 5. แผนถอยกลับ (เมื่อยอดไม่ตรง)
**ใครตัดสินถอย: เจ้าของ** (HQ เสนอพร้อมเหตุผล) · ถอยได้ทันทีโดยไม่กระทบอย่างอื่น **เฉพาะก่อนมีผู้ใช้บันทึกงานบนสัญญานำเข้า** — หลังจากนั้นใช้ทางกู้จากสำรอง (5.3)

### 5.1 ถอยทะเบียน (ลบด้วย `import_batch`)
ลำดับตาม FK (อ่านจาก migration):
- `customer_phones` → ลบตามลูกค้าเอง (CASCADE) · `contract_teams` → ลบตามสัญญาเอง (CASCADE)
- `contracts.customer_id` → customers เป็น **RESTRICT** → ต้องลบสัญญาก่อนลูกค้า
- `visits.contract_id` → contracts เป็น **RESTRICT** → **ถ้ามีคนบันทึกผลบริการบนสัญญานำเข้าแล้ว ลบไม่ได้ = หยุด** ไปใช้ 5.3
- stations / contract_files / missed_service_resolutions / todo → CASCADE ตามสัญญา (ตอนนำเข้าไม่มีแถวพวกนี้) · trigger `contracts_return_transferred_stations` ทำงานตอนลบแต่ไม่มีอะไรให้คืน
- ด่าน trigger: ไม่มี trigger ไหนกันการลบของ service_role / ผู้ดูแลฐานข้อมูล (ด่าน AG007 / M40 ดูเฉพาะผู้ใช้ที่ล็อกอิน) · RLS ไม่กระทบ service_role
- **audit_log จะมีแถว delete ทุกแถว** (สัญญา/ลูกค้า/เบอร์/ทีม ≈ 9,400 แถว) — ปกติ ไม่ต้องลบ audit

ทางที่เสนอ: สคริปต์ถอยกลับ (หัวข้อ 3 ข้อ 6) · ทางสำรองถ้ายังไม่มีสคริปต์ = ผู้ดูแลฐานข้อมูลรัน SQL ใน transaction เดียว (role postgres ของ SQL Editor — งานผู้ดูแลตาม runbook ไม่ใช่จากแอป/สคริปต์):
```sql
BEGIN;
CREATE TEMP TABLE rb ON COMMIT DROP AS
  SELECT id, customer_id FROM contracts WHERE import_batch = 'registry-OCT26';
SELECT count(*) FROM rb;                                                   -- ต้อง 2,369
SELECT count(*) FROM visits WHERE contract_id IN (SELECT id FROM rb);     -- ต้อง 0 ไม่งั้น ROLLBACK
DELETE FROM contracts WHERE id IN (SELECT id FROM rb);                    -- ทีมลบตาม
DELETE FROM customers cu
 WHERE cu.id IN (SELECT customer_id FROM rb)
   AND NOT EXISTS (SELECT 1 FROM contracts c WHERE c.customer_id = cu.id); -- เบอร์ลบตาม
SELECT count(*) FROM contracts WHERE import_batch = 'registry-OCT26';    -- ต้อง 0
-- ตรวจครบแล้วค่อย COMMIT; · ไม่ตรง = ROLLBACK;
```
หลังถอยแล้ว ตัวนำเข้ารันใหม่ได้ (ด่าน "มีข้อมูลเดิม = หยุด" จะผ่านเพราะไม่มีลูกค้าในสาขาเป้าหมายแล้ว)
